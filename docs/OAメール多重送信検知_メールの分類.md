# OAメール多重送信検知：メールの分類

検知の仕組みが、どのメールをどう扱うかの一覧である。
仕様の詳細は `OAメール多重送信検知_本文重複_仕様.md` を参照。

---

## 前提：何を「重複」と呼ぶか

| 項目 | 値 |
| --- | --- |
| 判定キー | **宛先 + 本文**（それぞれハッシュ化） |
| 判定窓 | 1時間 |
| 閾値 | 同じキーが **2件以上** |

**同じ人に、同じ内容が、1時間以内に2通以上**届いたときだけ異常とみなす。
一斉配信（同じ本文を多数の宛先へ）は宛先が違うため、原理的に検知対象にならない。

---

## 分類の軸

判定に効くのは次の2点だけである。

1. **送信ログが出るか** — 出なければ検知の土俵に乗らない
2. **本文が毎回変わるか** — 変われば重複にならない

---

## 分類

| # | 分類 | 代表例 | 送信ログ | 本文 | 検知 | 扱い |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | **既知の多重送信** | `inform-admin:registrants-status` | 出る | 同じ | **鳴る** | 記録するが**通知しない** |
| 2 | **繰り返し送られる通知** | 新着メッセージ、未読通知 | 出る | **毎回変わる** | 鳴らない | そのまま |
| 3 | **ユーザー操作起因** | パスワードリセット等 | **出ない** | — | 対象外 | そのまま |
| 4 | **その他すべて** | 上記以外 | 出る | 同じなら重複 | **鳴る** | **Slack へ通知** |

**4 が本来の検知対象である。** 1〜3 は「鳴らせたくない」「鳴りようがない」ものを整理したもの。

---

### 1. 既知の多重送信

`InformAdminAboutNewRegistrationsStatus` のループ構造の不具合により、同じ管理者へ同じ本文が複数通送られている。2026-09-17 の調査で、1日に **3通** 受け取っている受信者を実データで確認した。

**修正されるまでの間、毎朝この検知が鳴り続ける。** そのため件名のハッシュで**通知だけを抑止**する。記録は通常どおり残すため、修正後に発生状況を遡って確認できる。

除外（記録しない）ではなく抑止（記録するが通知しない）にしているのは、直ったことを検知の記録側で確認したいからである。

### 2. 繰り返し送られる通知

頻度が最も高い経路だが、**本文が毎回変わるため鳴らない。**

実測では、ある受信者が「メッセージが届きました」を50時間で **104通**、最短4分間隔で受け取っていた。本文ハッシュを比較したところ **5件すべて異なった**（本文長も 15,769〜18,421 とばらつく）。本文にメッセージ内容と発言時刻が含まれるためである。

| 判定方法 | この経路での結果 |
| --- | --- |
| 件名で判定 | **毎時鳴り続ける。使えない** |
| 本文で判定 | **鳴らない。正しい** |

**件名ではなく本文で判定している理由がここにある。**

なお5分間隔で動く送信系はすべて再送防止のガードを持つ。未読が続いてもメールは再送されない。

| 経路 | 起動 | 再送防止 |
| --- | --- | --- |
| `NewMessagesEmailer` | 5分 | `message_recipients.is_emailed = 1` |
| `NewMessagesAdminEmailer` | 5分 | 同上 |
| `NotificationsEmailer` | 5分 | `notification.is_emailed = true` |
| `NewGroupChatAdminMessagesEmailer` | 5分 | `last_read_date` を前進 |

### 3. ユーザー操作起因

**そもそも検知の対象外である。** 送信ログが出ないため、何通送られても検知側からは見えない。

理由は送信経路が worker を通らないことにある。

| 経路 | 状態 |
| --- | --- |
| `OAResetPassword`（パスワードリセット） | `emails` に行は作るが `send_status = 'cancelled'`。worker は送らず、Laravel の Notification が直接送信する |
| `ForgotPasswordController:160` | `Mail::send` で直接送信。`emails` に行を作らない |

仮にログが出ていたとしても鳴らない。リセットURLにはワンタイムトークンと `encrypt($email)` が含まれ、**どちらも毎回異なる値になる**ためである。

> **注意。** 「ユーザーが同じ操作を連打すると同じ本文が複数通出る」という懸念に対しては、上記のとおり心配ない。ただし裏を返すと、**この経路で本当に暴走が起きても検知できない。**

### 4. その他すべて

上記以外は通常の検知対象である。同じ宛先へ同じ本文が1時間以内に2通以上出れば Slack へ通知する。

---

## 判定の流れ

```
送信ログが出る？
│
├ 出ない ────────────────────→ 対象外（分類3）
│
└ 出る
   │
   ├ 同じ宛先・同じ本文が1時間で2件以上？
   │   │
   │   ├ ならない ───────────→ 正常（分類2 はここに落ちる）
   │   │
   │   └ なる
   │       │
   │       ├ 抑止リストの件名？
   │       │   │
   │       │   ├ はい ───────→ 記録するが通知しない（分類1）
   │       │   │
   │       │   └ いいえ ─────→ Slack へ通知（分類4）
```

---

## 検知できないもの

| 事象 | 理由 |
| --- | --- |
| 1時間を超えて離れた重複 | 判定窓の外 |
| 一斉配信 | 判定キーに宛先を含むため、そもそも異常にならない |
| 同じ宛先への異なる本文 | 本文が違えばキーが変わる |
| `Mail::send` で直接送るメール | 送信ログが出ない（分類3） |
| 送られるべきメールが送られていない | 本仕様の対象外 |

## 誤検知の要因

| 要因 | 対応 |
| --- | --- |
| ログの再送（Fluent Bit） | `logTimestamp` の優先順位を修正する |
| 同一文面の連投 | 対応しない（成立条件が4つ重なる必要があり、既読が付けば送信自体が止まる） |
| `inform-admin:registrants-status` | 通知を抑止する（分類1） |
