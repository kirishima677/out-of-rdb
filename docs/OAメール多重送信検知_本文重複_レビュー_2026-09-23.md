## 判定

**実装前に仕様の修正が必要。P1が2件、P2が5件。** 宛先と正規化した本文を組み合わせる方針、HMAC、別テーブル、保存後の強整合Queryは採用可能。ただし、送信の識別方法と本文の同一性について、調査結果からは成立しない前提がある。

本レビューは本文重複検知の仕様を主対象とする。既知の `inform-admin:registrants-status` を抑止して導入する合意は前提として尊重する。アプリ不具合の修正を、本機能導入の必須条件とはしない。

確認対象はローカルの資料、検知本体、4本のテスト／ベンチマーク、およびLaravelの関連実装。参照時のHEADは `out-of-rdb: 5676719`、`official-alumni: da8c39bf29`。本番のデプロイ内容との一致や、資料にある本番集計値は再検証していない。アプリ、既存仕様、検知本体の変更は行っていない。

## 指摘

### R1 [P1] `logTimestamp` の種類数では、本物の同時送信を消してしまう

該当：[本文重複仕様：再送対処案](/Users/nishiokahiroki/code/out-of-rdb/docs/OAメール多重送信検知_本文重複_仕様.md:800)

Laravel行頭の時刻は秒単位。同じ宛先・本文について、EmailIDが100と101のメールがともに `09:00:00` に送られた場合、時刻の種類数は1であり、検知したい2通を捕捉できない。仮にEmailIDと時刻の組を数えても、同じEmailIDを別ワーカーが同じ秒に送る事象は1件になる。時刻の優先順位変更だけでは、現行のレコード数カウントに再送行が加算される問題も解消しない。

現在のSKは処理時刻を含むため、同じS3オブジェクトを再処理すると別行として保存される。実際の `handler` を、S3・DynamoDB・Slackだけメモリ内の代替に置き換えて同じイベントを2回渡したところ、1回目は正常、2回目は重複1件・通知1回になった。S3自身も同一イベントの重複配送を起こし得るため、Fluent Bit以外の再処理も扱う必要がある。[AWS公式：S3イベントの配送保証](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-how-to-event-types-and-destinations.html)

推奨：実送信ごとに一度生成してログへ残す `send_event_id` 等を定義し、再配送でも変わらない識別子で数える。S3の再処理防止と、別オブジェクトに入ったFluent Bit再送の識別を分けて検討する。現状の情報だけで同一ホスト・同一秒の同一送信ログを完全に区別できるとは保証しない。本文の生成重複に限れば異なるEmailIDの数を数える方法もあるが、同一EmailIDの再送は既存検知側で引き続き扱う必要がある。

### R2 [P1] 本文の可変値は `email_id` だけではない

該当：[本文重複仕様：全数調査の結論](/Users/nishiokahiroki/code/out-of-rdb/docs/OAメール多重送信検知_本文重複_仕様.md:709)

テンプレート自体だけでなく、テンプレートへ渡す値が毎回変わる。

- `NotifiableTrait::createNotificationEmail()` は、Verified、Room Approval、Room Invite、Mention、New Post等の `target_url` に通知レコードの `notif_id` を付ける。[NotifiableTrait.php](/Users/nishiokahiroki/Hackazouk/official-alumni/app/Traits/NotifiableTrait.php:245)
- このURLはボタンへそのまま入り、開封画像の `url` パラメータにもURLエンコードされて入る。[action-button.blade.php](/Users/nishiokahiroki/Hackazouk/official-alumni/resources/views/emails/redesign/components/action-button.blade.php:14)、[container.blade.php](/Users/nishiokahiroki/Hackazouk/official-alumni/resources/views/emails/redesign/layout/container.blade.php:11)
- 管理者向けChange Emailは、`bcrypt()` で毎回変わる `enc_user` / `enc_mail` と、30分後の有効期限表示を本文へ渡し、`emails` 経由で送る。[UserController.php](/Users/nishiokahiroki/Hackazouk/official-alumni/app/Http/Controllers/UserController.php:863)

同一業務イベントについて通知レコードが二重生成されると、文面・宛先が同じでも `notif_id` が異なるため、提案の正規化では本文ハッシュが一致しない。これは生成側不具合を見つけるという目的の取りこぼしになる。PHPで提案どおりの正規化とHMACを実行し、`email_id` のみの差は吸収され、`notif_id` の差が残ることを確認した。

推奨：生成側からテンプレートまでの経路単位で可変値を整理する。通知識別用の `notif_id` を同一内容判定から外すなら、通常URLと開封URL内のエンコードされた値の両方を扱う。投稿ID、ルームID、セキュリティトークン等を一律に削除せず、残す値と検知対象外にする経路を明記する。

また、現行の正規表現は本文全域へ適用されるため、利用者の投稿に含まれる `email_id=10` と `email_id=11` も同一化する。正規化対象はOAが付ける既知のURL・パラメータに限定するのがよい。

### R3 [P2] 正常操作でも本文が一致する経路が、想定より広い

該当：[メール分類：「Bは鳴らない」の根拠](/Users/nishiokahiroki/code/out-of-rdb/docs/OAメール多重送信検知_メールの分類.md:89)、[本文重複仕様：連投の4条件](/Users/nishiokahiroki/code/out-of-rdb/docs/OAメール多重送信検知_本文重複_仕様.md:814)

少なくとも次の2経路では、「同じ分の連投・5分刻みの境界・10分未読」という条件を必要としない。

1. **管理者向けNew Room Messages。** メールへ渡すメッセージ情報は本文と送信者名で、発言時刻やメッセージIDを含まない。ルームと未読件数等も同じなら本文は一致する。例えば09:05の通知後に管理者が既読にし、同じ人が同じルームへ同文を新しく投稿し、09:10に未読1件として通知される場合、正常な別投稿なのに重複判定になる。[生成するデータ](/Users/nishiokahiroki/Hackazouk/official-alumni/app/Console/Commands/NewGroupChatAdminMessagesEmailer.php:254)、[メールの表示内容](/Users/nishiokahiroki/Hackazouk/official-alumni/resources/views/emails/redesign/new_room_messages.blade.php:201)
2. **イベント参加→取消→再参加。** コントローラは参加レコードを削除・復元し、各操作で通知を生成する。参加メールは参加者・イベント・参加者一覧等から作られ、操作時刻を含まない。他の参加者等が変わらなければ、最初と再参加時のメールは `email_id` 正規化後に一致する。[EventController.php](/Users/nishiokahiroki/Hackazouk/official-alumni/Modules/Posts/Http/Controllers/EventController.php:53)、[PostInteractedMail.php](/Users/nishiokahiroki/Hackazouk/official-alumni/Modules/Posts/Jobs/PostInteractedMail.php:125)

これはコードから確認できる成立条件であり、本番での発生頻度は未測定。「本文重複」を検出する判定自体は正しいが、それを直ちに「不具合」と判定することはできない。

推奨：DMの5件の実測を全16経路に一般化しない。上記を正常操作の許容例として仕様・運用へ追加し、まず実測する。全体の閾値を先回りして引き上げる必要はない。通知は調査対象となる重複候補として扱う。

### R4 [P2] 異常時の読み取り量は線形ではなく、現行ベンチマークでは評価できない

該当：[本文重複仕様：処理時間見積もり](/Users/nishiokahiroki/code/out-of-rdb/docs/OAメール多重送信検知_本文重複_仕様.md:342)

1行保存するたび同じキーの全件を数えるため、同一キーにN行集中すると `1 + 2 + ... + N` 件を累計で評価する。`COUNT` でも読み取り容量は実アイテムを読む場合と同じで、1MBを超えると追加のQueryが発生する。[AWS公式：Query](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_Query.html)

現行 `_count_recent()` を代替テーブルで実行して、次の累計件数を確認した。これは論理的な読み取り量の確認であり、AWS上のRCUや時間の実測ではない。

| 同一キーの行数 | 累計で評価する件数 | 全行が別キーの場合 |
| --- | --- | --- |
| 350 | 61,425 | 350 |
| 2,400 | 2,881,200 | 2,400 |

[既存ベンチマーク](/Users/nishiokahiroki/code/out-of-rdb/scripts/benchmark-mail-duplicate-detector.sh:122) は各行に別EmailIDを割り当てるため、この負荷を踏まない。新機能では別EmailIDが同じ本文キーに集中するケースこそ重要。通常の宛先分散時にPK設計を直ちに問題視する必要はないが、異常時の集中負荷について「約2倍・60秒で収まる」とは言えない。通知を全行処理後に送るため、タイムアウトすると検知済みでも重複通知まで進まない。

推奨：同一本文キーへの集中、1MB超のページング、並列実行を検証する。対策候補は、一定単位の全書き込み後にキーごとに一度数えること、または閾値到達の判定と正確な総数集計を分けること。並列時の取りこぼしを防ぐため、保存→強整合読み取りの順序は維持する。現流量での容量限界は未測定。[AWS公式：パーティション設計と容量](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html)

### R5 [P2] 処理時刻の1時間窓では、日次メールが窓の外になる保証がない

該当：[本文重複仕様：判定窓](/Users/nishiokahiroki/code/out-of-rdb/docs/OAメール多重送信検知_本文重複_仕様.md:22)

例えば、前日09:00と当日09:00に正常送信された同文の日次メールが、ログ滞留解消後の同じLambda実行で初めて処理されると、両方の `createdAt` が同じになり異常判定される。EmailIDもLaravel出力時刻も異なるため、R1の再送行除去では防げない。

資料は遅延を認識しているが、「日次・週次だから窓の外」という分類と両立していない。反対に、実送信は近接していてもログ配送が1時間以上離れれば取りこぼす。

推奨：処理時刻による検知を採用するなら、この正常メールの誤検知も許容条件へ記載する。「実送信が1時間以内」を保証したいなら、イベント時刻、遅延・順不同の許容範囲、保存期間を合わせて設計する。`logTimestamp` の優先順位変更だけで窓の問題も解決したことにしない。

### R6 [P2] ドライランSQLはローリング窓を再現せず、実在する重複を除外する

該当：[本文重複仕様：ドライランSQL](/Users/nishiokahiroki/code/out-of-rdb/docs/OAメール多重送信検知_本文重複_仕様.md:864)

同一キーが09:00、09:30、10:30に出現すると、09:00と09:30の2通で検知条件を満たす。しかし全グループの `MAX - MIN = 90分` なので、SQLはグループ全体を結果から落とす。何時間も続く重複ほど過少評価する。`TIMESTAMPDIFF(MINUTE)` による切り捨てで、60分を少し超えたものを含める差もある。

さらにSQLはDBの `send_schedule` を使い、Lambdaは処理時刻を使う。DBの `content` を直接読む一方、アプリの `$email->content` にはアクセサによるHTML等の変換も入る。[Email.php](/Users/nishiokahiroki/Hackazouk/official-alumni/app/Email.php:95)

推奨：時刻順に並べ、別の1件が正確に3600秒以内に存在するかで判定する。「そのままSlackへ飛ぶ」という説明は削除し、送信時刻を使う候補調査であることを明記する。検知本体との一致検証にはログ配送時刻と同じ正規化処理を使ったリプレイが必要。

### R7 [P2] Change Email（Alumni）は、一覧の分類と異なり検知対象外

## 依頼された6観点への回答

| 観点 | 回答 |
| --- | --- |
| 1. 宛先＋本文・1時間・2件で誤検知を防げるか | 調査候補の検知には使える。正常操作による一致がR3にあり、配送遅延の影響もR5にある。「不具合確定」とは扱えない |
| 2. `email_id` の正規化だけで足りるか | 足りない。R2の `notif_id` と生成側の可変値がある |
| 3. `logTimestamp` の種類数でよいか | 不十分。R1の同時送信を潰す。送信イベントの識別方法が必要 |
| 4. DynamoDBのキー設計 | 宛先＋本文のPK、固定幅UTCと行番号を含むSK、ベーステーブルの強整合Queryは妥当。再処理の一意性と集中時の読み取り量はR1・R4で修正が必要 |
| 5. `subject_hash` の抑止 | 現在の固定2件名に限定し、記録を残す暫定策として妥当。検知種別と混在バッチの扱いを明文化するとよい |
| 6. `createLog()` の追記が送信処理を壊すリスク | 提案の文字列処理・HMAC単体に即時の致命的欠陥は確認していない。ただし成功後と送信エラー処理中の両方から呼ばれるため、ログ項目追加の失敗が送信状態・障害通知へ波及しない検証が必要 |

### 抑止について詰める点

- 固定件名の日本語・英語は翻訳ファイルと一致する。同一件名の別原因も隠れるトレードオフは、仕様に既に記載されている。
- 仕様の通知条件はEmailID検知も含む形で記述されており、「本文重複だけを抑止する」とは確定していない。既知の生成側不具合だけを抑止する目的なら、同じEmailIDの再送まで抑止するかを明確にする。前の回答で「本文重複通知のみ」と断定したのは正確でなかった。
- 同じS3オブジェクトに既知事象と別の異常が混在するときは、抑止対象だけを集計から外し、非対象の異常は通知する必要がある。オブジェクト全体を抑止しない。
- 鍵変更時は抑止用の2件名ハッシュも変わるため、ワーカーの鍵と抑止リストの更新手順を揃える。

### 追加ログの安全性・調査手順

- PHPで、null・空文字・非UTF-8バイト・長めの本文に対する正規化とHMACを実行し、16桁の結果が得られることを確認した。現在の正規表現には `/u` がないため、「不正UTF-8で失敗する」はこのパターンの説明として適切ではないが、`null` フォールバック自体は残せる。
- 正常な `mail_to` が1宛先の文字列配列である前提では、追記案の処理は単純。ただし複数宛先では、1宛先ごとの送信ログに同じ配列全体のハッシュが入り誤検知する。これは資料で既に未確定。実装時には対象を単一Toに限定するか、実際に送信した宛先を渡すかを決める。CC/BCCは現在のキーに含まれない。
- `createLog()` は送信成功の保存後にも、`critical` 経路にも入る。追加計算が失敗した場合の既存ログ・障害通知継続、成功状態の維持を確認する。[EvenSendEmails.php](/Users/nishiokahiroki/Hackazouk/official-alumni/app/Console/Commands/EvenSendEmails.php:361)
- `rawLog` の `content` はメール本文ではなく `Email <id> was successfully sent!` 等の処理メッセージ。[仕様の「rawLogから元のメッセージ本文を確認」](/Users/nishiokahiroki/code/out-of-rdb/docs/OAメール多重送信検知_本文重複_仕様.md:853) は成立しない。EmailIDを使って `emails.content` や元メッセージを調査する手順が必要。
- `created_at` が同一でも同じ実行だったとは断定できず、数分差でも正常操作とは断定できない。調査の手がかりとして使い、原因を決める条件にしない。

## 検証範囲と追加すべきテスト

今回実行したのは外部接続なしの論理再現。Pythonは検知本体の関数をそのまま読み込み、S3・DynamoDB・Slackを代替した。PHPは提案の正規化・HMACを合成データへ適用した。Laravel全体の起動、メール送信、本番AWSへのアクセス、既存LocalStack結合テストの実行は行っていない。

| 今回の確認 | 結果 |
| --- | --- |
| 同じS3オブジェクトを1秒差で2回処理 | 現行コードは2件保存し、2回目に重複通知 |
| 別EmailID・同じ秒の時刻を種類数で集計 | 時刻は1種類になり、2通を区別できない |
| 同一キー350行／2,400行の反復カウント | 累計61,425件／2,881,200件を評価 |
| PHP：`email_id` のみ異なる | 正規化後のハッシュは一致 |
| PHP：`notif_id` も異なる | 正規化後もハッシュは不一致 |
| PHP：本文中の `email_id=10` / `email_id=11` | 業務本文も誤って同一化 |
| PHP：Change Email相当のbcrypt URL | ハッシュは不一致 |
| 09:00、09:30、10:30のドライラン判定 | ローリング窓は成立、現SQLのグループ条件は不成立 |

本文重複を実装する際は、既存の正常系・同一ファイル・並行保存に加え、次を確認する。

1. 別EmailID・同一宛先・同一本文は検知し、別宛先／別本文は検知しない。
2. 同じ秒の本物の2送信を保持し、同一S3イベント再配送と別オブジェクトのログ再送は重複送信として数えない。
3. 通知レコード二重生成の `notif_id` 差、開封画像内のエンコードURL、通常の投稿IDの差を扱い分ける。
4. ルーム通知とイベント再参加の正常一致を、合意した方針どおり扱う。
5. 抑止対象のみ・非対象のみ・混在・EmailID重複と本文重複の同時成立を検証する。
6. 旧ログのハッシュ欠損、空値、不正なコンテキストでも、本文検知の異常を可視化しつつ既存EmailID検知を維持する。
7. 単一キー集中、1MB超のページング、並行処理、1時間境界、古いログの一括配送を検証する。
8. アプリ側の成功ログ、送信失敗、`critical`、鍵未設定・全ワーカー統一・設定キャッシュを確認する。

既存の並行テストは保存件数を確認するがSlack到達は確認しない。既存ベンチマークは重複の集中負荷を測らない。このため、前の回答の「テストは十分」という評価は本文重複機能の受け入れ判断には使えない。
