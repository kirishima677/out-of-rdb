# OAメール多重送信検知：メールの分類・判定・検知の限界

更新日：2026-09-24

**今回追加するのは「同じ宛先に、同じ内容のメールが繰り返し送られた候補」を見つける検知です。通知は不具合の確定ではなく、内容を確認するきっかけです。**

本書は、メールごとの扱いと、検知できること・できないことをチームで共有するための資料です。本文重複検知の導入後の方針を説明しています。既存のEmailID重複検知は稼働中ですが、今回追加する本文判定・ログ再送対策・通知停止機能は、確認したローカルの検知本体にはまだ実装されていません。

## 1. 何を重複と判定するか

| 検知 | 比べるもの | 見つけたいこと |
| --- | --- | --- |
| 既存：EmailID重複 | メール行のID | 同じメール行が複数回送信された |
| 今回追加：本文重複 | 宛先と、比較用に整えたメール本文 | 別のメール行として作られていても、同じ宛先へ同じ内容が複数回送信された |

判定条件は、**検知側のログ処理時刻で直近1時間に、同じ判定キーの異なる送信が2回以上**です。「送信から1時間待って通知する」という意味ではなく、条件が成立したログの処理時に検知します。

- 本文は、開封・通知識別用のURLパラメータ `email_id` と `notif_id` の数値の違いを吸収して比較します。件名だけでは判定しません。
- 意味が似た文章を判定する仕組みではありません。比較対象の本文が違えば、同じ内容に見えても一致しないことがあります。
- 送信ごとに付ける識別子 `send_event_id` で回数を数えます。同じログの再送・再配送は1回、同じ秒の別送信は2回として扱う設計です。
- メールの送信後にログを調べます。多重送信そのものを止める機能ではありません。

| 例 | 今回の本文判定 |
| --- | --- |
| Aさんに同じ本文を2回送った | 条件を満たせば検知する |
| AさんとBさんに同じ本文を1回ずつ送った | 宛先が違うため、これだけでは検知しない |
| Aさんに同じ件名・異なる本文を送った | 本文が違うため、これだけでは検知しない |
| 1回の送信ログが2回届いた | 送信識別子が同じなら1回として扱う |
| 正常な別操作の結果、Aさんに同じ本文が2回届いた | 検知する。不具合かどうかは確認が必要 |

## 2. メールごとの分類と対応

**分類の基準は「今回の検知が読む送信成功ログを出す経路か」です。** 即時・5分ごと・日次・週次といった起動間隔だけでは決まりません。5分バッチも週次ダイジェストも、条件を満たせば検知します。

元のメール一覧に対応する44項目を掲載しています。名称は照合しやすいよう原資料の英語表記を残しています。対象欄のAlumniはアルムナイ、Employeeは従業員、Adminは管理者です。

| 分類 | 検知・通知の扱い |
| --- | --- |
| 対象 | EmailID・本文の両方を判定。条件成立時はSlack通知の候補になる |
| 対象・正常一致に注意 | 同じ判定を行うが、正常操作でも本文が一致する例がある。現時点で一律に除外しない |
| 通知抑止 | 判定・記録を続け、既知の件名についてSlack通知を抑止する |
| EmailIDでカバー | ログは対象。別生成時に本文が変わるため、今回の本文判定では捉えにくい |
| 対象外 | 今回読む送信成功ログが出ず、どちらの検知でも捉えられない |
| 要確認 | 原資料と実装経路の対応が未確認。監視できているとは扱わない |

「対象」は必要なログ項目が揃っている前提での分類です。実際の通知には判定条件と抑止設定が適用されます。全経路の実機検証が完了したことを示すものではありません。

## 3. 検知した後、どう扱うか

通常は、条件を満たしたものを重複候補としてSlackへ通知します。複数件をまとめ、**検知処理1回につき最大1通**に集約する設計です。メール1通ごとにSlack通知を出すわけではありません。

登録未完了ユーザーの管理者向け日次メール（No.14）は、既知の同文多重生成があるため、日本語・英語の該当件名について通知を抑止します。**検知対象から外すのではなく、検知・記録は続けます。** 同じ件名の別原因による重複も通知されなくなる点には注意が必要です。

| 状況 | チームでの扱い |
| --- | --- |
| 通常の重複候補 | メール内容と生成・送信の経緯を確認する |
| 既知事象の件名に一致 | 記録を残し、Slack通知を抑止する。修正確認後に抑止を解除する |
| 正常操作による同文と確認できた | 不具合と断定しない。発生頻度を見て、必要なら抑止の範囲を検討する |
| 新しい本文検知の通知が多すぎる | 特定件名の抑止、次に本文重複通知だけの一時停止を検討する |
| 通知全体を止める必要がある | 全種別の通知を停止できる。保存・判定は継続する |

本文通知だけを止める場合、既存のEmailID重複通知は継続できます。ただし、件名による抑止や全体停止が別途有効な場合は、その設定も適用されます。

確認では、ログからEmailIDを特定してメール本文や元の操作を調べます。**ログの中にメール本文そのものは入っていません。** 生成時刻の差は手がかりになりますが、「近いから不具合」「24時間差だから正常」とは時刻だけで断定しません。

## 4. 検知できないこと・今回の対象にしないこと

| 範囲・限界 | チームが理解しておくこと |
| --- | --- |
| 送信成功ログが出ない経路 | 直接送信等は見えない。DBにメール行があっても、今回のログが出るとは限らない |
| 本文が一致しない重複 | 別生成でURL・トークン・有効期限等が変われば、受信者には同じ内容に見えても捉えられない場合がある |
| 1時間の判定窓をまたぐ重複 | どの1時間にも2送信が揃わなければ捉えられない。長時間続く事象の全件数を把握する仕組みではない |
| ログ配送の遅延 | 昨日と今日の正常メールが同時に処理されると検知する場合がある。逆に近接送信でもログ到着が1時間以上離れると取りこぼす |
| 同じ宛先への異なる本文の大量送信 | 今回の本文重複条件では捉えない。送信量の急増を監視する機能ではない |
| 多数の宛先への1回ずつの一斉配信 | それだけでは重複にしない。ただし同じ宛先への繰り返しがあれば判定対象になる |
| メールの未送信・欠落・受信箱への到達 | 「送られるべきものが送られなかった」ことや、迷惑メール振り分け・受信箱到達は保証しない |
| 正常操作か不具合かの確定 | 同文の再リマインド、別のルーム投稿、イベント再参加等の理由は、通知後に確認する |
| 複数To・CC/BCC | 宛先ごとの判定方法は未確定。単一Toの調査結果を、すべての宛先構成へ一般化しない |
| 旧ログ・手動送信経路 | 追加ハッシュがないログでは本文検知ができない。送信識別子がない旧ログでは再配送の誤検知リスクが残る |
| 通知の重複・頻度 | 「1処理につき最大1通」は全体の通知回数上限ではない。別の処理で同じ事象を再び通知する可能性がある |

今回の送信識別子による対策は、**同じ送信ログのコピーを二重に数えないためのもの**です。昨日と今日に実際に送った2通が、ログ遅延で同時に届く問題までは解消しません。

## 5. 検知の速さ・処理量

検知の速さは、**ログが届くまでの待ち時間＋検知処理時間**で決まります。メール送信と同時の通知ではありません。

| 項目 | 現時点で共有できること |
| --- | --- |
| ログ配送待ち | 既存構成の資料には、ログ出力から保存まで約1分47秒という実測がある。ログのフラッシュは約10分間隔で、滞留時にはさらに遅れる。通知までの保証時間ではない |
| 今回追加後・350ログ行 | 処理時間は約9秒の見積もり。新機能の実測ではない |
| 今回追加後・2,400ログ行 | 処理時間は約60秒の見積もり。新機能の実測ではない |
| 同じ宛先・本文への集中 | 全行保存後、比較するキーごとに1回だけ数える設計へ変更する。実装後に集中負荷での検証が必要 |
| 処理のタイムアウト | 設定は300秒。通知を処理の最後に送るため、途中で時間切れになるとSlack通知まで進まない場合がある |
| 検知率・正常操作による通知頻度 | 数値としては未確定。既存事例や一部メールの調査結果を全メールの検知率とは扱わない |

日次・週次のまとめ配信や、同一キーへの大量集中で、見積もりどおりに処理できるかを確認してから性能を確定します。
