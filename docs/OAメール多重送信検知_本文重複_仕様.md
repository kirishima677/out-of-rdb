# OAメール多重送信検知：本文重複（宛先重複）

> 既存の「送信側重複（EmailID 重複）」検知への追加仕様。
> 基本設計・構築手順・運用は既存文書を引き継ぐ。差分のみをここに記す。

## 目的

**同じ受信者に、同じ内容のメールが複数通届く状態を検知する。**

EmailID が異なるため、既存の検知では原理的に捕捉できない。

## 検知対象

| 項目 | 内容 |
| --- | --- |
| 判定キー | **宛先 + 本文** |
| 判定窓 | 1時間（既存と同じ） |
| 閾値 | 2件以上（既存と同じ） |

### 判定窓について

**何を基準に1時間を測るか。** DynamoDB に保存したレコードの `createdAt` で測る。これは **Lambda がそのログ行を処理した時刻**であり、メールが送信された時刻でも、ログが出力された時刻でもない。

既存の EmailID 検知と同じ基準である。同じテーブル・同じ判定ロジックを流用するため、窓の定義も揃えている。

**この基準には既知の弱点がある。** Fluent Bit がログを遅れて送出した場合、古いログ行が「今」のものとして扱われる。実際に 2026-09-15 に 5日遅れの再送が発生している（「ログの再送」の節を参照）。対処案も同節に記載。

#### 処理時刻で測ることの限界（レビュー指摘 R5・許容する）

`send_event_id` で再送は解決するが、**窓を処理時刻で測ること自体の限界は残る。** 方向が2つある。

| 状況 | 起きること |
| --- | --- |
| ログの配送が滞留し、前日09:00と当日09:00の日次メールが**同じ実行で処理された** | 両方の `createdAt` が同値になり、**正常な2通を重複と判定する** |
| 実送信は数秒差だが、ログの配送が1時間以上離れた | **本物の重複を取りこぼす** |

1つ目は `send_event_id` では防げない。**本物の別送信なので識別子は異なり、正しく2件と数えられてしまう。**

**これを消すには、窓の基準を送信時刻（イベント時刻）に変える必要がある。** そのためには遅延の許容範囲・順不同の扱い・レコードの保持期間をまとめて設計し直すことになる。**現時点では採用しない。**

代わりに、通知で判別できるようにする。ログに `created_at`（`emails` 行の作成時刻）を入れてあるため、**通知本文に `created_at` の幅を出せば、受け取った側が即座に切り分けられる。**

```
created_at が 24時間離れている → 日次メールの滞留。正常
created_at が 数秒以内         → 調査対象
```

「日次・週次だから判定窓の外」という整理は、**ログの配送が正常な場合にのみ成り立つ。**

#### 1時間より長くできない

日次の登録リマインドは、同じ宛先へ同じ本文を繰り返し送る。**24時間以上に広げると、これが全件誤検知になる**（前提条件3）。

#### 1時間より短くしてもよいが、揃える利点が大きい

実データで見つかった重複は3秒差だった。窓を15分程度に縮めても捕捉できる。ただし既存の検知と窓が揃っていれば、テーブルの TTL も判定ロジックも共通のまま使える。**分ける理由が生じるまでは1時間とする。**

#### 窓を超えた重複は検知できない

`inform-admin:registrants-status` は実行に数時間かかり、同一実行でも作成時刻が分散する（2026-09-17 の実測で 00:00:09 〜 05:07:14）。**1時間以上離れた組は捕捉できない。** 「毎朝鳴るが、実際の重複はもっと多い」という状態になる。

## 判定条件のまとめ

**EmailID 重複と本文重複を通した、通知に至るまでの全条件。** 既存検知の条件も含む。

### 実行の順序

```
Lambda 起動（S3イベント1件）
│
├ now を固定  ──────────────── この実行で保存する全レコードの createdAt になる
│
├ オブジェクトごとに繰り返し
│  │
│  ├ ① プレフィックス判定 ──── 外れたらここで終了。GetObject もしない
│  │
│  └ ログ行ごとに繰り返し（1行ずつ展開しながら）
│     │
│     ├ ② 正規表現で判定 ───── 外れたら次の行へ
│     │
│     ├ ③ 保存（EmailID テーブル）      → キーを控えておく
│     └ ④ 保存（本文テーブル）          → キーを控えておく
│
└ 全行を保存し終えてから
   ├ ⑤ 控えたキーごとに1回だけ件数を数える ← 行ごとには数えない
   ├ ⑥ 抑止判定
   └ ⑦ Slack へ通知（多くても1回）
```

#### 順序に理由がある箇所

**`now` を最初に固定する。** 1回の実行で処理した全レコードの `createdAt` が同値になる。判定窓の基準・保存時刻・通知時刻がずれない。結果としてソートキーの先頭が同じ値になるため、**一意性は行番号が担う**。

**プレフィックス判定はオブジェクトを読む前。** 対象外なら `GetObject` を呼ばない。フィルタなし構成では起動の9割以上が対象外のため、ここで捨てられるかが処理時間に効く。

**保存してから数える。** 逆順にすると、同時実行している別の Lambda が「自分より前には無い」と判断して双方が取りこぼす。書いてから `ConsistentRead` で数えれば、自分の分も相手の分も必ず見える。

**数えるのは全行を保存し終えてから、キーごとに1回。** 行ごとに数えると、同じキーがN行あるときに `1 + 2 + … + N` 件を評価することになる（レビュー指摘 R4）。まとめて数えれば N 件で済む。同時実行との関係は変わらない。**保存が先、カウントが後**という順序は保たれている。

**通知は最後に1回。** 行ごとには送らない。1つのオブジェクトに300件の重複があっても Slack へ飛ぶのは1通で、本文には規模だけを載せる。

**抑止は通知の直前。** 保存もカウントも通常どおり行い、Slack へ送る段階だけで判断する。抑止してもデータは残るため、後から件数を数えられる。

#### ③④は対になっている

| | EmailID | 本文 |
| --- | --- | --- |
| 保存 | ③ | ④ |
| キー | `18929861` | `<mail_to_hash>:<content_hash>` |
| 件数 | ⑤で両方まとめて | 同じ |
| 判定 | 1時間に2件以上 | 同じ |

**判定ロジックは共通で、キーが違うだけである。** 書き込みが1行あたり1回から2回に増える。カウントは行数ではなく**キーの種類数**に比例する。

### 1. 入口：ログ行を拾うか

以下をすべて満たした行だけが判定対象になる。1つでも外れれば、その行は無視される。

| # | 条件 | 外れた場合 |
| --- | --- | --- |
| 1-1 | S3 オブジェクトキーが `TARGET_KEY_PREFIX` に前方一致 | `Skip out-of-scope object` を出力し、オブジェクトを読まずに終了 |
| 1-2 | **行頭から**正規表現に一致 | 無視 |
| 1-3 | コマンドが `EvenSendEmails` / `OddSendEmails` / `SendEmails` | 無視 |
| 1-4 | `success sending email: <数字>` の形 | 無視（`failed` は対象外） |

**行頭一致にしている理由。** Laravel のログ末尾には context JSON が付き、そこにメールの件名（利用者由来の文字列）が入る。行中一致にすると、件名に文字列を仕込むことで偽の重複を発生させられる。

前置部分（`[日時] channel.INFO: `）は任意グループだが、**存在する場合は `.INFO` でなければならない**。`.ERROR` などのレベル違いは対象外になる。

### 2. 保存

条件を満たした行は、**2つのテーブルへ1レコードずつ**書き込まれる。

| テーブル | パーティションキー |
| --- | --- |
| `${ENV_PREFIX}mail_send_log_events` | `EmailID` |
| `${ENV_PREFIX}mail_send_log_events_by_content` | `mail_to_content_hash` |

### 3. 異常の判定

**保存した直後に、そのキーの件数を数える。** 判定条件は両者で共通。

```
直近1時間に同じキーのレコードが 2件以上
```

- 「直近1時間」は `createdAt`（Lambda がログ行を処理した時刻）で測る
- 自分が今書いたレコードを含む。`count >= 2` は「自分 + 他に1件以上」
- `ConsistentRead=True` のため、他の Lambda が並行して書いたレコードも必ず数に入る

| 検知 | 異常の意味 | 想定される原因 |
| --- | --- | --- |
| EmailID 重複 | **同じメール行が2回送信された** | 再試行、ステータスの戻し、ログの再送 |
| 本文重複 | **同じ宛先へ同じ内容が2通以上送られた** | 生成側の不具合、ログの再送 |

### 4. 通知するか

異常と判定しても、**通知しない場合がある。**

**判断は上から順に行う。**

| # | 条件 | 動作 |
| --- | --- | --- |
| 1 | `NOTIFY_DISABLED` が設定されている | **全種別の通知を止める。** `MAIL_DUPLICATE_NOTIFY_DISABLED` を出力 |
| 2 | `NOTIFY_DISABLED_CONTENT` が設定されている | **本文重複の通知だけ止める。** EmailID 重複は通知する |
| 3 | `subject_hash` が `SUPPRESS_SUBJECT_HASHES` に含まれる | その件名だけ止める。`MAIL_DUPLICATE_SUPPRESSED` を出力 |
| — | 上記以外 | Slack へ通知 |

**いずれの場合も、保存とカウントは通常どおり行う。** 止めるのは Slack への送信だけである。

通知本文には個別の EmailID を列挙せず、**重複の規模のみ**を載せる。件数が増えても本文の長さは変わらない。

### 5. 検知できないもの

| 事象 | 理由 |
| --- | --- |
| **1時間を超えて離れた重複** | 判定窓の外。`inform-admin:registrants-status` は実行が数時間に分散するため一部が該当する |
| 一斉配信 | 判定キーに宛先を含むため、そもそも異常にならない |
| 同じ宛先への異なる本文 | 本文が違えばキーが変わる |
| `Mail::send` で直接送るメール | `emails` テーブルを通らず、送信ログが出ない |
| 送られるべきメールが送られていない | 本仕様の対象外 |

### 6. 誤検知の要因

| 要因 | 状況 | 対応 |
| --- | --- | --- |
| **ログの再送・S3 の再配送** | 同じログ行が1時間以内に2回届いた場合 | `send_event_id` の種類数で数える（「ログの再送」の節） |
| **正常操作で本文が一致する** | 管理者向けルーム通知、イベント再参加 | **対応しない。許容する**（「正常な動作でも鳴るケース」の節） |
| **ログ滞留による時刻の圧縮** | 日次メールの2日分が同じ実行で処理された場合 | **対応しない。許容する**（「判定窓について」） |
| **同一文面の連投** | 4条件が同時に成立した場合 | 対応しない（「連投による誤検知」の節） |
| 既知の不具合 | `inform-admin:registrants-status` | 通知を抑止する（「既知事象の通知抑止」の節） |

> **通知は「不具合の確定」ではなく「調査対象の候補」である。** 上記3つは正常な動作でも鳴る。通知を受けたら `emails` テーブルで中身を確認する運用を前提とする。

## 検知対象としないこと

- **一斉配信。** 同じ本文を多数の宛先へ送るのは正常動作である。判定キーに宛先を含めるため、原理的に検知対象にならない
- **同じ宛先への異なる本文。** 新着メッセージ通知など、頻度が高くても本文が異なれば対象外
- **送られるべきメールが送られていないこと。** 本仕様の対象外

## 実データによる裏付け（2026-09-17 調査）

本番の `emails` テーブル 20,000行（約50時間ぶん）を調査した。

### 事象は実在する

`InformAdminAboutNewRegistrationsStatus`（`inform-admin:registrants-status`、日次）で、**毎日発生している**。

| 日 | 影響 |
| --- | --- |
| 2026-09-15 | NTT の管理者が同一メールを **7通ずつ** 受信 |
| 2026-09-16 | ABeam の管理者24人が同一メールを **8通ずつ** 受信 |
| 2026-09-17 | 継続中 |

受信者は顧客企業の管理者である。

### 原因

`InformAdminAboutNewRegistrationsStatus.php` のループ構造。

```php
foreach ($registrants as $registrant) {        // 登録者ごと
    foreach ($company_users as $user) {        // 管理者ごと
        AlumniIncompleteRegistrationEmail::create(..., $registrants, $registrant, ...);
    }
}
```

`AlumniIncompleteRegistrationEmail::create()` が組み立てる本文に、**登録者を識別する情報が一切含まれていない**。`$registrant` は `mail_object_id` に使われるのみ、`$registrants` は渡されているが未使用である。

```php
'body' => trans('email.redesign.admin_remind_alumni.body', [
    'team_name' => $company->website,
    //'count' => count($registrants)      // コメントアウトされている
], $language),
```

コメントアウトされた `count` から、**元は「N件の未完了登録があります」という1通の要約メールだった**と読める。件数表示を外した際にループ構造が残り、人数ぶんの重複送信になったと推測される。

集計では、各管理者の受信通数（`n`）とその日の対象登録者数（`registrants`）が**全行で一致**した。

さらに本文の同一性を直接確認した。

```sql
SELECT (SELECT content FROM emails WHERE id = 18932796)
     = (SELECT content FROM emails WHERE id = 18932806) AS identical;
-- → 1
```

この2件は `mail_object_id` が 77462 / 77461 と**別の登録者**でありながら、宛先が同じで、**本文がバイト単位で完全一致**する。本文が登録者の情報を一切持たないことの直接的な証明である。

なお実行時間が長く、同一実行でも作成時刻が数時間にわたって分散する（2026-09-17 の実測で 00:00:09 〜 05:07:14）。**1時間の判定窓を超える組は検知できない。** 「毎朝鳴るが実際の重複はもっと多い」という状態になるため、**検知の稼働前にこの不具合を修正すべきである。**

**これは検知を待たずに修正できる不具合である。** メール作成を登録者ループの外に出し、管理者1人につき1通とするのが本筋。

### 誤検知は起きない

最も頻度の高い経路で確認した。ある受信者は「メッセージが届きました」を50時間で **104通**、**最短4分間隔・1時間あたり最大8通**受け取っていた。

本文ハッシュを比較したところ、**5件すべて異なった**（長さも 15,769〜18,421 とばらつく）。新着メッセージ通知の本文にはメッセージ内容と発言時刻が含まれるため、別の発言に対する通知は別の本文になる。

| 判定方法 | この経路での結果 |
| --- | --- |
| 件名で判定 | **毎時鳴り続ける。使えない** |
| 本文で判定 | **鳴らない。正しい** |

### 繰り返し送信される経路の確認

5分間隔で動く送信系はすべてワンショットのガードを持つ。

| 経路 | 起動 | 再送防止 |
| --- | --- | --- |
| `NewMessagesEmailer` | 5分 | `message_recipients.is_emailed = 1` |
| `NewMessagesAdminEmailer` | 5分 | 同上 |
| `NotificationsEmailer` | 5分 | `notification.is_emailed = true` |
| `NewGroupChatAdminMessagesEmailer` | 5分 | `last_read_date` を前進 |
| `NewGroupChatAlumniMessagesEmailer` | **未登録** | 稼働していない |
| 週次ダイジェスト・登録リマインド | 日次・週次 | 無し（24時間以上あく） |

**未読が続いてもメールは再送されない。** 「10分経っても既読にならないと飛ぶ」通知は、メッセージ1件につき1回のみである。したがってリマインダーの間隔を考慮する必要はない。

## 構成

**既存の Lambda に相乗りする。** 新しい Lambda は作れない。

S3 は同一バケットで条件が重なる通知設定を許可せず（構築手順書 5-2）、プレフィックスフィルタも機能しないため、**1つのバケットに登録できる消費者は1つだけ**である。新しい Lambda を作ってもイベントを受け取る手段がない。

既存 Lambda はログ解析・窓判定・ページング・通知をすべて持つため、判定キーを1本増やすだけで済む。

| | 既存 | 追加 |
| --- | --- | --- |
| テーブル | `${ENV_PREFIX}mail_send_log_events` | `${ENV_PREFIX}mail_send_log_events_by_content` |
| パーティションキー | `EmailID` = `18929861` | `mail_to_content_hash` = `<mail_to_hash>:<content_hash>` |
| ソートキー | `{createdAt}#{sourceKey}#{行番号}` | 同左 |

**同じログイベントを、別のキーで持ち直した表である。** テーブル名の `_by_content` はその関係を表す。

## DynamoDB への影響

**本文重複検知の専用テーブルを新設する。既存テーブルは一切変更しない。**

```
${ENV_PREFIX}mail_send_log_events_by_content
  パーティションキー  mail_to_content_hash (S)  = "<mail_to_hash>:<content_hash>"
  ソートキー          recordKey    (S)  = "{createdAt}#{sourceKey}#{行番号}"
  TTL                 expiresAt
  課金                オンデマンド
```

判定ロジックは既存と共通である（`Key(...).eq(key) & Key("recordKey").gte(cutoff)` + `ConsistentRead`）。キー名が違うだけで、窓も閾値もページングの扱いも変わらない。

### なぜ別テーブルにしたか

当初は既存テーブルに `B#` の接頭辞で相乗りする案だった。**運用対象を増やさない**ことを優先したためである。以下の理由で別テーブルへ変更した。

| 理由 | 内容 |
| --- | --- |
| **名前が正しくなる** | 相乗り案では `EmailID` 列に EmailID でない値が入る。キー属性名は作成後に変更できない |
| **撤退が容易** | 本文重複検知が不要になった場合、テーブルを削除するだけで完了する。相乗りだと該当レコードだけを取り除く作業が発生し、消し忘れると混在したまま残る |
| **コスト差が無い** | オンデマンド課金にテーブル単位の固定費は無い。1つでも2つでも請求は同じ |

コストが判断材料にならないことが確認できたため、運用の手間と設計の素直さで選んだ。

### 格納されるレコード

既存テーブルと同じ属性に、`emailId` を加える。

```
mail_to_content_hash       = "a1b2c3d4e5f6a7b8:9f8e7d6c5b4a3210"
recordKey          = "2026-09-17T00:01:30.123456+00:00#.../abc.gz#22"
createdAt          = "2026-09-17T00:01:30.123456+00:00"
emailId            = "18932806"        ← キーではなく通常属性
command            = "OddSendEmails"
sourceBucket / sourceKey / sourceLineNumber
rawLog
sourceHost
expiresAt
```

**`emailId` は重複検知後の追跡に使う。** `mail_to_content_hash` だけでは元のメールに戻れない。

### 具体例

2026-09-17 に実在した重複（`18932796` と `18932806`、同一宛先・同一本文）を処理すると、2つの表は次のようになる。

**既存テーブル** — 別々のパーティションに1件ずつ

| `EmailID` | `recordKey` |
| --- | --- |
| `18932796` | `...#12` |
| `18932806` | `...#22` |

```
Query EmailID = 18932796  →  1件  →  正常
Query EmailID = 18932806  →  1件  →  正常
```

**新テーブル** — 同一パーティションに2件

| `mail_to_content_hash` | `recordKey` | `emailId` |
| --- | --- | --- |
| `a1b2c3d4e5f6a7b8:9f8e7d6c5b4a3210` | `...#12` | `18932796` |
| `a1b2c3d4e5f6a7b8:9f8e7d6c5b4a3210` | `...#22` | `18932806` |

```
Query mail_to_content_hash = a1b2...:9f8e...  →  2件  →  重複検知
```

**パーティションキーが同じでも上書きされないのは、ソートキーが行番号を含むため。** この2行は同一実行・同一オブジェクトのため `createdAt` と `sourceKey` が同値であり、行番号だけが両者を分けている。既存設計で詰めた箇所がそのまま効いている。

### 処理の内訳

**書き込みは行ごと、カウントはキーごと。**

```
ログ行ごと
  1. put_item   既存テーブル   PK = 18929861
  2. put_item   新テーブル     PK = <mail_to_hash>:<content_hash>

全行の保存が終わってから、控えたキーごとに1回だけ
  3. query      既存テーブル   PK = 各 EmailID,    SK >= cutoff
  4. query      新テーブル     PK = 各 本文キー,    SK >= cutoff
```

**保存してから数える。** `ConsistentRead=True` により、自分が書いた行も他の Lambda が並行して書いた行も必ず数に入る。`count >= 2` は「自分 + 他に1件以上」を意味する。順序を逆にすると同時実行時に取りこぼす。

#### 通常時

宛先が分散していれば、キーの種類数 ≒ 行数である。書き込みが倍になる分だけ増える。

| | 現状 | 追加後 |
| --- | --- | --- |
| 1行あたり | 12.7ms | 約25ms |
| 通常（350行/オブジェクト） | 4.4秒 | 約9秒 |
| ピーク（2,400行） | 30秒 | 約60秒 |

タイムアウト300秒に対しては十分だが、**余裕が半分になる**。稼働後に実測を取り直すこと。

#### 異常時（同じキーに集中した場合）

**行ごとに数えると、読み取り量が行数の二乗で効く。** これは検知したい事象そのもので発生する（レビュー指摘 R4）。

| 同一キーの行数 | 行ごとに数える | **キーごとに1回数える** |
| --- | --- | --- |
| 350 | 61,425 件 | **350 件** |
| 2,400 | 2,881,200 件 | **2,400 件** |

`Select="COUNT"` を指定しても**読み取り容量は実アイテムを読む場合と同じ**である。件数だけが返るのは転送量の話であって、RCU は減らない。

1回の `Query` は最大1MBまでしか評価せず、超過分は `LastEvaluatedKey` として持ち越される。**全ページ読み切る実装を維持すること**（打ち切ると件数が過少になる）。

> **タイムアウトすると通知まで到達しない。** 検知も保存も済んでいるのに Slack へ飛ばない状態になる。異常時ほど重くなる設計なので、ここは実装時に必ず検証する。

### 導入時に必要な作業

本文重複検知の実装時に行う。**構築手順書への反映も同時に行う**（現時点の手順書は現行構成を記述しているため、先行して変更しない）。

| 項目 | 内容 |
| --- | --- |
| テーブル作成 | `create-table` + TTL 有効化 |
| IAM | インラインポリシーの `DetectionTableAccess` の `Resource` を配列にし、新テーブルの ARN を追加 |
| Lambda 環境変数 | `CONTENT_TABLE_NAME` / `SUPPRESS_SUBJECT_HASHES` を追加（合計5つ）。`NOTIFY_DISABLED` / `NOTIFY_DISABLED_CONTENT` は**未設定を既定**とし、必要時のみ追加する |
| 運用コマンド集 | 状態確認と調査のコマンドに新テーブルを追加 |

環境変数が5つになるため、**`--environment` の全置換で書き落とす対象が2つ増える**（付録C-3 / D-1）。

緊急停止用の2つは**平常時は設定しない**。設定されている状態そのものが異常を示すようにしておく。

## ログへの追加項目

`EvenSendEmails.php` と `OddSendEmails.php` の `createLog()` に項目を追加する。両ファイルは `id % 2` の条件と `throttleSending()` の位置以外ほぼ同一であり、同じ修正を2箇所に入れる。

```php
private function createLog($email, $log_message, $type, $add_to_errnotif = true)
{
    $key  = (string) config('mail_dup.hash_key');
    $to   = is_array($email->mail_to) ? implode(',', $email->mail_to) : (string) $email->mail_to;

    // 1通ごとに変わるが内容としては同じ値を、URL のクエリパラメータに限って落とす。
    // 素の形（?a=1 / &a=1 / &amp;a=1）と、開封画像の url= に入る
    // URL エンコード形（%3Fa%3D1 / %26a%3D1）の両方が対象。
    $body = preg_replace(
        '/([?&]|&amp;|%3F|%26)(email_id|notif_id)(=|%3D)\\d+/i',
        '$1$2$3',
        (string) $email->content
    ) ?? (string) $email->content;

    $logData = [
        "mail_object_type" => $email->mail_object_type,
        "mail_object_id"   => $email->mail_object_id,
        "subject"          => $email->subject,
        "scheduled_at"     => $email->send_schedule,
        "content"          => $log_message,

        "created_at"       => $email->created_at,
        "company"          => trim(substr(strrchr('|' . $email->mail_from, '|'), 1)),
        "language"         => $email->language,
        "send_event_id"    => bin2hex(random_bytes(16)),

        "content_hash"     => substr(hash_hmac('sha256', $body, $key), 0, 16),
        "mail_to_hash"     => substr(hash_hmac('sha256', strtolower(trim($to)), $key), 0, 16),
        "subject_hash"     => substr(hash_hmac('sha256', (string) $email->subject, $key), 0, 16),
    ];
```

### 修正するのは2ファイルだけでよい

同じ `createLog()` は `SendEmails.php:358` にも存在し、Lambda の正規表現も `SendEmails` を受け付ける（「1. 入口：ログ行を拾うか」の 1-3）。**それでも修正対象は `EvenSendEmails` / `OddSendEmails` の2ファイルとする。**

| コマンド | ファイル | スケジュール | 修正 |
| --- | --- | --- | --- |
| `send_even_emails` | `EvenSendEmails.php:378` | `Kernel.php` に登録済み | **する** |
| `send_odd_emails` | `OddSendEmails.php:378` | `Kernel.php` に登録済み | **する** |
| `send_emails` | `SendEmails.php:358` | **登録されていない**（`$commands` にあるのみ） | しない |
| — | `OldSendEmails.php` | 登録されていない | しない |

`send_emails` は定期実行されておらず、手動でしか動かない。

> **ただし手で流された場合、そのぶんは検知されない。** `content_hash` を持たないログが出るため、Lambda は EmailID の重複しか見られない。運用で `send_emails` を使う機会が生じたら、そのときに同じ修正を入れる。

### 命名

**追加する項目名は、由来となるカラム名に揃える。**

| 元のカラム | 項目名 |
| --- | --- |
| `content` | `content_hash` |
| `mail_to` | `mail_to_hash` |
| `subject` | `subject_hash` |

`send_event_id` だけは由来カラムを持たない。**この送信のために新規に発行する値**であるため、カラム名ではなく役割で名付けている。

既存の項目（`mail_object_type`、`scheduled_at` など）がスネークケースであるため、記法もそれに合わせる。

DB を見ている人が `mail_to` を見てログの `mail_to_hash` を見れば、対応関係を考えずに済む。`recipient` のような別語を導入すると「何を指すのか」を確認する手間が生じる。

> **`content_hash` は `MD5(content)` と一致しない。** `email_id` を正規化したうえで HMAC をかけているため。素の `content` のハッシュではない点に注意する（正規化の理由は前提条件1を参照）。

### 各項目の意図

| 項目 | 用途 |
| --- | --- |
| `content_hash` | 判定キーの一方。`email_id` を正規化してから算出する |
| `mail_to_hash` | 判定キーの一方。生アドレスはログに出さない |
| `subject_hash` | 既知事象の通知抑止に使う |
| `send_event_id` | **件数を数える単位。** ログの再送・S3 の再配送を1件にまとめる（「ログの再送」の節） |
| `created_at` | **切り分けの主軸**（下記） |
| `company` | 通知に影響範囲を出せる。`mail_from` の後半が会社を表す |
| `language` | 同じ通知で本文ハッシュが異なる理由の説明（言語別テンプレート） |

**3つのハッシュを別々に出す。** 組み合わせは Lambda 側で作れる。分けておけば、後から「同じ本文が大量配信された」「特定の宛先に大量に届いた」を検知したくなったときに**アプリ側の変更が不要**になる。デプロイを要する変更は今回だけにしたい。

### `created_at` が切り分けの主軸になる

重複を検知したとき、`created_at` の見え方で原因の当たりがつく。

| `created_at` | 示唆 |
| --- | --- |
| 2件が**同一** | 1回の実行で複数作られた。**生成側の不具合**（`inform-admin:registrants-status` がこの形） |
| 2件が**5分前後離れる** | 別の tick で作られた。**連投による誤検知**の可能性 |
| そもそも EmailID が同じ | 同じ行が2回送られた。既存の EmailID 検知の担当 |

現在の `scheduled_at`（`$email->send_schedule`）は、送信処理が直前に `Carbon::now()` で上書きするため、**実質「送信時刻」である**。項目名と内容が一致していない。`created_at` を並べて置くことで、「生成」と「送信」の2軸が揃う。

### 入れない項目

| 項目 | 理由 |
| --- | --- |
| `mail_to`（生アドレス） | ハッシュで足りる。ログに個人情報を増やさない |
| `content`（本文） | 数KB。ログ量が跳ねる。ハッシュで足りる |
| `opened_at` / `clicks` | 送信時点では常に null |
| `send_status` | 成功ログでは常に `sent` |
| `unsubscribe_for` / `as_plaintext` / `is_edited` | `mail_object_type` と重複、または調査で使う場面が稀 |

### デプロイ後の確認

変更は `createLog()` の中で完結し、送信処理そのものには触れない。確認は3点。

| 確認 | 見るもの |
| --- | --- |
| 新項目が出ている | `content_hash` / `mail_to_hash` / `subject_hash` / `created_at` / `company` |
| 既存の検知が壊れていない | `success sending email: <id>` の形式が変わっていないこと |
| エラーが増えていない | Laravel ログに警告が出ていないこと |

2点目が重要である。Lambda の正規表現はメッセージ部の先頭にしか依存しないため、コンテキスト JSON に項目が増えても壊れない。形式が変わっていないことだけ確認する。

**STG でも実際の送信ログは出る**（2026-09-17 実測で11件/日）。ただし件数が少なく発生タイミングも任意ではないため、**デプロイ直後に確認できるとは限らない**。数時間待つ想定を持っておく。

```bash
Y=$(date -u +%Y); M=$(date -u +%m); D=$(date -u +%d)
BASE="service=worker/env=staging/log_source=laravel-app/year=${Y}/month=${M}/day=${D}/"
rm -rf /tmp/stglog; mkdir -p /tmp/stglog
aws s3 cp "s3://hkz-log-archive/${BASE}" /tmp/stglog/ --recursive --quiet
find /tmp/stglog -name '*.gz' -print0 | xargs -0 zcat 2>/dev/null \
  | grep -E 'success +sending email:' | tail -1 | python3 -m json.tool
```

### 例外への備え

`preg_replace` は PCRE の制限（`pcre.backtrack_limit` 超過など）に当たると `null` を返す。`createLog()` は `critical` 経路で管理者への通知メールを送る入口でもあるため、ここで落ちると**障害通知そのものが失われる**。`?? (string) $email->content` のフォールバックを必ず付ける。

> **`/u` 修飾子は付けていない。** 付けないことで不正な UTF-8 が含まれていても PCRE はバイト列として処理し、失敗しない。対象が ASCII のクエリパラメータのみであるため、`/u` は不要である。「不正な UTF-8 で null になる」は本パターンには当てはまらない（レビュー指摘）。

他の追加処理は null でも安全に動く。`mail_from` が null なら会社は空文字、`mail_to` が null でも空文字、鍵が未設定でも空の鍵でハッシュは計算される（逆引き耐性が落ちるだけで、検知は成立する）。

### ハッシュ鍵について

**何の鍵か。** `content_hash` / `mail_to_hash` / `subject_hash` を計算する **HMAC-SHA256 の秘密鍵**である。本仕様で新たに導入する。

**なぜ鍵付きにするか。** ログに残るハッシュから元の値を逆引きされないため。素の SHA-256 だと、メールアドレスや定型文のように候補が限られる値は総当たりで復元できてしまう。宛先アドレスをログに出さずハッシュにしている意味が失われる。

| 項目 | 内容 |
| --- | --- |
| 置き場所 | アプリの設定（`config('mail_dup.hash_key')`。実体は環境変数） |
| 必要な範囲 | **アプリのワーカーのみ。** `EvenSendEmails` / `OddSendEmails` が動く全インスタンス |
| Lambda | **不要。** 検知側はハッシュを比較するだけで、計算しない |

**Lambda に鍵を渡す必要はない。** アプリ側が計算した値をそのまま突き合わせるだけである。Lambda の環境変数に鍵を追加する作業は発生しない。

#### 追加するファイル

`config/mail_dup.php` を新規に作成する。

```php
<?php

return [
    /*
     * メール多重送信検知のログに出すハッシュの HMAC 鍵。
     * EvenSendEmails / OddSendEmails の createLog() から参照する。
     * 全ワーカーで同一の値を設定すること。
     */
    'hash_key' => env('MAIL_DUP_HASH_KEY', ''),
];
```

環境変数は各ワーカーに次を追加する。

```
MAIL_DUP_HASH_KEY=<32文字以上のランダム文字列>
```

値の生成例。

```bash
openssl rand -hex 32
```

> **`env()` を config ファイルの外で呼ばないこと。** `config:cache` を実行すると、config ファイル以外の `env()` は `null` を返す。`createLog()` から直接 `env('MAIL_DUP_HASH_KEY')` を呼ぶと、キャッシュの有無で**ハッシュ値が変わる**。検知が静かに壊れるため、必ず `config('mail_dup.hash_key')` 経由で読む。

#### 満たすべき条件

- **全ワーカーで同一であること。** インスタンスごとに違うと、同じ本文が別のハッシュになり検知できない
- **時間をまたいで安定していること。** デプロイのたびに変わる値（リリースIDなど）を使うと、過去のハッシュと突き合わせられない

#### ローテーション

鍵を変えると、その時点で過去のハッシュと繋がらなくなる。判定窓（1時間）より十分長い間隔とすること。実質的には、**当面固定で運用してよい**。

#### 未設定の場合

空文字の鍵としてハッシュが計算される。**検知そのものは成立する**（全ワーカーで同じ「空の鍵」を使うため）。失われるのは逆引き耐性だけである。設定漏れで検知が止まることはない。

## 既知事象の通知抑止

`inform-admin:registrants-status` の重複は**既知の事象であり、修正時期は未定**である（2026-09-17 に確認。「申請未完了ユーザーの扱い全般」の見直しに含める想定）。

検知をそのまま稼働させると、**初日から毎朝この事象で通知が飛ぶ**。そのため抑止を入れる。運用チームとは「ログは出すが Slack へは通知しない」で合意済み。

### 方針：除外ではなく抑止

**検知・保存・ログ出力は通常どおり行い、Slack 通知のみ行わない。**

処理ごと飛ばすと次が見えなくなるため。

- 規模が増えても気づかない
- 修正されたかどうかが分からない
- **同じ通知で別の原因による重複が起きても見えない**

抑止したことはログに残し、件数を後から数えられるようにする。

```text
MAIL_DUPLICATE_SUPPRESSED known-issue subject=<hash> emailIDs=3
```

### 抑止リストの持ち方

**Lambda の環境変数として持つ。**

```
SUPPRESS_SUBJECT_HASHES=a1b2c3d4e5f6a7b8,9f8e7d6c5b4a3210
```

カンマ区切りの `subject_hash` の一覧。空または未設定なら抑止しない。

#### DynamoDB に置かない理由

当初は DynamoDB の設定アイテムとして持つ案だった。`update-function-configuration --environment` が**環境変数マップを全置換する**ため、運用中に変わる設定を `TABLE_NAME` を消しうる操作の後ろに置きたくない、という理由である（付録C-3 / D-1）。

しかし検知イベント用のテーブルに設定アイテムを置くと、**`mail_to_content_hash` 列にハッシュでない値が入る**。列名と中身を一致させるために別テーブルを選んだ判断と矛盾する。

**抑止リストが変わるのは実質2回である。** 不具合の発覚時に追加し、修正時に削除する。頻繁に触る設定ではないため、全置換の手順を2回踏むコストは許容できる。

失うのは、抑止の理由と解除条件を属性として持てる点である。**本書に記載することで代替する**（下記「解除条件」）。

Lambda はコンテナ起動時に環境変数を読むため、実行あたりの追加コストは無い。

### 判定に使う値

件名そのものではなく **`subject_hash`** で比較する。アプリ側の `createLog` で `content_hash` / `mail_to_hash` と同時に出力する。

日本語の固定文字列を Lambda に埋め込まずに済み、ログのコンテキスト JSON を解析する処理も不要になる。

### 件名が可変の場合（現状は該当しない）

`lang/jp/email.php` の件名49件のうち、**27件はプレースホルダを含む**（`:team_name` など）。残り22件が固定値である。

**今回の抑止対象 `admin_remind_alumni` は固定値**であり、問題にならない。

```
jp: 新しいユーザー（回答未完了）から登録がありました。
en: A user has yet to complete registration.
```

`AlumniIncompleteRegistrationEmail::create()` は管理者の `preferred_language` で切り替えるため、**2つのハッシュを登録する**。会社が増えても変わらない。

#### 可変の件名を抑止したくなった場合の問題

`:team_name` を含む件名は、**会社ごとに別のハッシュ**になる。

| 問題 | 内容 |
| --- | --- |
| 数が増える | 会社数 × 言語数のハッシュが必要 |
| **新しい会社で抑止が外れる** | 追加を忘れると、その会社ぶんだけ通知が飛び始める |

失敗の仕方は安全側（鳴りすぎ）だが、**誰も覚えていない保守作業**が発生する。

#### そのときの選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | DB から全件名を取得しハッシュを列挙 | 動くが、会社追加のたびに再生成が必要 |
| B | `mail_object_type` で抑止 | `App\Alumni` などが広すぎて使えない |
| **C** | **通知種別をログに出す**（翻訳キー `admin_remind_alumni` 相当） | 会社にも言語にも依存しない。本質的な解決 |

Cが正解だが、**各メール生成クラスに種別を渡す改修**が必要であり、`createLog()` 1箇所の変更とは規模が違う。

**現時点では実装しない。** 可変件名の抑止が実際に必要になった時点で、それが C を導入する判断材料になる。

### トレードオフ

**件名単位の抑止であるため、同じ通知で別の原因による重複が発生しても隠れる。**

抑止件数を定期的に確認し、平常時から大きく外れていないかを見ること。

```bash
aws logs tail "/aws/lambda/${FUNCTION_NAME}" --since 24h | grep -c MAIL_DUPLICATE_SUPPRESSED
```

### 解除条件

`inform-admin:registrants-status`（または申請未完了ユーザーまわりの処理）が修正され、重複が発生しなくなったとき。設定アイテムを削除するだけで通常動作へ戻る。

## 通知

既存と同じチャンネルへ、**種別を区別できる本文**で送る。個別の EmailID や宛先は列挙せず、規模のみを伝える方針は既存を踏襲する。

### 通知の緊急停止

誤検知が続いたとき、**Slack への通知だけを環境変数で止められるようにする。**

| 環境変数 | 効果 | 想定する使い所 |
| --- | --- | --- |
| `NOTIFY_DISABLED_CONTENT` | 本文重複の通知のみ停止 | **通常はこちら。** 新機能の誤報で、実績のある EmailID 検知まで止めたくない |
| `NOTIFY_DISABLED` | 全種別の通知を停止 | 最後の手段 |

**2段に分ける理由。** EmailID 検知は 2026-09-16 から本番で安定稼働している。本文重複は新規であり、誤報の可能性が高いのは明らかにこちらである。**1つのフラグにすると、新機能の誤報を止めるために実績のある検知を道連れにすることになる。**

#### 止めるのは通知だけ

保存もカウントも通常どおり行う。**停止中に起きた重複は、解除後に DynamoDB から遡って数えられる。** 既知事象の抑止（`SUPPRESS_SUBJECT_HASHES`）と同じ原則である。

#### 値には理由と日付を入れる

```
NOTIFY_DISABLED_CONTENT=2026-09-25 R3の頻度調査中
```

**`1` や `true` にしない。** 空でなければ有効とする。こうしておくと `get-function-configuration` を見ただけで「なぜ」「いつから」が分かる。

**緊急停止の最大のリスクは解除し忘れである。** 静かになった時点で忘れられ、数週間後に「検知が動いていない」と気づく。値そのものに理由を書くことが、最低限の歯止めになる。

#### 停止中も件数は見える

停止時は `MAIL_DUPLICATE_NOTIFY_DISABLED` をログに出す。**メトリクスフィルタを張れば、Slack が静かなままでも CloudWatch で発生件数を追える。** 停止したまま状況が分からなくなることを防ぐ。

```bash
aws logs tail "/aws/lambda/${FUNCTION_NAME}" --since 24h | grep -c MAIL_DUPLICATE_NOTIFY_DISABLED
```

#### まず件名の抑止を試す

**通知は1回の Lambda 実行につき最大1通である。** 対象オブジェクトは12件/時なので、**最悪でも12通/時**にしかならない。数百通が飛ぶ事態にはならない。

したがって手順は次の順になる。

1. 通知本文から原因の件名を特定し、`SUPPRESS_SUBJECT_HASHES` に追加する（**第一手**）
2. 原因が特定できない、または複数種別にまたがる場合に `NOTIFY_DISABLED_CONTENT`
3. それでも収まらない場合に `NOTIFY_DISABLED`

#### 環境変数を変更するときの注意

> **`--environment` は環境変数マップを全置換する。** 慌てて実行すると `TABLE_NAME` や `CONTENT_TABLE_NAME` を書き落とし、既定値へフォールバックする。**緊急時こそ、現在値を読んでマージする手順を使うこと**（構築手順書 付録C-3 / D-1）。
>
> 停止は緊急対応であり、最も操作を誤りやすい場面である。**事前にマージ用のコマンドを運用コマンド集に用意しておく。**

## 前提条件

**いずれかが崩れると、無言で誤検知するか、無言で検知しなくなる。**

### 1. 本文のハッシュ化前に `email_id` を除去する

**本文には既にメール1通ごとに異なる値が埋め込まれている。** 素のハッシュでは大半のメールが検知対象外になる。

`template.blade.php` は `layout/container.blade.php` を読み込み、開封トラッキング用の画像を出力する。

```blade
<img src="{{ route('open_mail', ['email' => $email, 'email_id' => $em_id_pop, ...]) }}" alt="" style="height: 0px;">
```

`$em_id_pop` はテンプレートの `@section('email_id', ...)` から来る。**このセクションを持つテンプレートは25個**あり、`daily_digest`・`new_dm`・`admin_digest`・`new_room_messages` など主要な通知が含まれる。これらは URL に `email_id=<数値>` が入るため、**内容が同一でも本文ハッシュが必ず異なる**。

一方 `generic_notification` はこのセクションを持たないため `email_id` が null となり、本文は内容だけで決まる。**実データで確認した重複事例（`inform-admin:registrants-status`）が検知できたのは、この経路だったためである。**

| テンプレート | `email_id` の埋め込み | 素のハッシュでの検知 |
| --- | --- | --- |
| `generic_notification` | 無し | **可能** |
| `daily_digest` / `new_dm` / `admin_digest` ほか24種 | **有り** | **不可能** |

#### 対処

ハッシュ化の前に、**1通ごとに変わるクエリパラメータを落とす。**

```php
$body = preg_replace(
    '/([?&]|&amp;|%3F|%26)(email_id|notif_id)(=|%3D)\\d+/i',
    '$1$2$3',
    (string) $email->content
) ?? (string) $email->content;

"content_hash" => substr(hash_hmac('sha256', $body, $key), 0, 16),
```

**パラメータ名だけでなく、直前の `?` `&` `&amp;` `%3F` `%26` も一致条件に入れている。** 本文全域に `/email_id=\\d+/` を当てると、利用者の投稿に含まれる `email_id=10` のような文字列まで同一化してしまう。クエリパラメータの位置に限定することで、OA が付けた値だけを対象にできる。

`%3F` / `%26` を含めるのは、開封トラッキング画像の `url=` パラメータに遷移先URLが**URLエンコードされて**入るためである。素の形だけを見ると、画像URLの中に残った `notif_id` を取りこぼす。

**正規化を入れないと、検知できるのは一部のメールだけになる。** しかも「検知されない」という失敗の仕方であるため、動いているように見えたまま大半を取りこぼす。

`open-email` ルートはクエリ文字列を使う GET であるため（`routes/web.php:20`）、この正規化で除去できる。本番の実データで形式を確認済み。

```text
//api-app.official-alumni.com/open-email?email=xxx%40gmail.com&amp;email_id=18889603&amp;url=...&amp;type=alumni
```

`email_id` の値はその行の `id` と一致する。

#### 一通ごとに変わる値（2026-09-23 更新）

> **2026-09-17 の調査はテンプレート（blade）しか見ておらず、PHP から渡される値を見落としていた。** レビュー指摘 R2 により `notif_id` を追加した。「`email_id` の1箇所で足りる」という当初の結論は誤りである。

| 値 | 入る場所 | 扱い |
| --- | --- | --- |
| `email_id` | 開封トラッキング画像（`layout/container.blade.php:11`、`layout/active_notifications_template.blade.php:307`） | **正規化する** |
| `notif_id` | `NotifiableTrait::createNotificationEmail()` が `target_url` に付与（`app/Traits/NotifiableTrait.php:245` ほか**26箇所**）。ボタンの `href` と、開封画像の `url=` にエンコードされて入る | **正規化する** |
| `bcrypt()` の値 | 管理者向け Change Email の `enc_user` / `enc_mail`（`UserController.php:863`） | **正規化できない**（下記） |
| 時刻（`Carbon::now` / `date()`） | テンプレート内に0件 | — |
| 乱数・UUID・トークン | テンプレート内に0件 | — |
| 配信停止URL | `renderUnsubscribeUrl($type)` は config から組み立てる | — |
| 送信時の外側テンプレート（`emails.default`） | `$email->content` の外側でありハッシュ対象外 | — |

##### `notif_id` を落とさないと何が起きるか

**検知したい事象そのものが検知できない。** 生成側の不具合で通知レコードが二重に作られた場合、文面も宛先も同じだが `notif_id` が別になる。正規化しなければ本文ハッシュが一致せず、**偽陰性**になる。

失敗の仕方が「鳴らない」であるため、動いているように見えたまま取りこぼす。`email_id` と同じ性質の問題である。

##### 正規化できない経路

管理者向け Change Email（`UserController.php:863`）は `bcrypt($new_email)` と `bcrypt($user->id)` を URL に含む。**bcrypt はソルトが毎回変わるため、同じ入力でも必ず別の文字列になる。** 加えて30分後の有効期限が本文に表示される。

この経路は送信ログこそ出るが、**本文ハッシュによる検知は原理的に成立しない。** 記録は残るので、EmailID の重複検知は従来どおり機能する。

##### 調査方法の限界

今回の一覧は「テンプレート」と「テンプレートへ値を渡す PHP」の両方を見たものだが、**全経路を機械的に網羅したわけではない。** 新しい通知メールを追加する際は、`target_url` に一通ごとに変わる値を付けていないかを確認すること。

#### 正規化しない値

同じ画像URLに受信者アドレス（`email=`）と遷移先（`url=`）も入るが、いずれも**受信者やスレッド単位であり、メール1通ごとには変わらない**。宛先を別のキーとして持つため判定に影響しない。

将来「同じ本文が多数の宛先へ送られた」を検知する場合はアドレスの正規化が要るが、本文には宛名も含まれるため、それだけでは受信者間の本文は一致しない。現時点では対象外とする。

#### 併せて確認すること

`@if(!$forcePlainText)` により、宛先ドメインが `forcedPlainTextEmailDomains` に含まれる場合はトラッキング画像が出力されない。**同じ種類のメールでも、宛先ドメインによって本文の構造が変わる。** 正規化を入れればどちらでも同じ結果になるが、前提として認識しておく。

#### 検知の対象外

送信ログが出力されないメールは本仕様の対象外である。**経路は2種類ある。**

| 経路 | 例 |
| --- | --- |
| `emails` テーブルを通らず `Mail::send` で直接送信 | `emails.welcome`、エラー通知、`ForgotPasswordController:160` |
| `emails` に行は作るが worker が拾わない状態で保存し、別経路で送信 | `OAResetPassword`（`cancelled`）、`ConfirmConnectedAccount`（`cancelled`）、`AlumniController::changeEmail()`（**`sent`**） |

**2種類目に注意する。** `emails` に行があるため DB 上は送信済みに見えるが、worker は `scheduled` の行しか処理しないため送信ログが出ない。一覧表の `Sending Schedule` 列だけでは判別できない（レビュー指摘 R7）。

**分類は一覧表ではなく、実際に呼ばれている送信関数で決める。**

### 2. 5分間隔の送信経路にワンショットのガードがあること

新しい通知メールを追加する際、`is_emailed` 相当の仕組みが無いと反復送信となり、**正常動作として重複が検知され続ける**。

`NewGroupChatAlumniMessagesEmailer` は現在スケジュールに登録されていないが、`unread_count > 0` を条件に送る作りである。**登録すると未読が続く限り送り続ける可能性がある。**

### 3. 判定窓を24時間以上に広げない

日次の登録リマインドは、同じ宛先へ同じ本文を繰り返し送る。窓を24時間以上にすると全件が誤検知になる。

## 未確定事項

### 宛先が複数のケース

`send_emails()` は宛先1件ごとに呼ばれ、末尾で `createLog()` を実行する。

```php
foreach ($email->mail_to as $each_mail_to) {
    $this->send_emails($email, $each_mail_to, $mail_object);
}
```

**1つのメールに宛先が2件あると、同じ EmailID のログが2行出力される。** 既存の EmailID 重複検知にとって誤検知の要因となる。

**2026-09-17 の調査時点では、20,101行すべてが宛先1件**であった（`JSON_LENGTH(mail_to)` で確認）。現時点で誤検知は発生しない。

ただし複数宛先を回すコード自体は存在するため、**将来そのようなメールを作る経路が追加されると、既存の EmailID 検知が誤検知する**。メール作成側を変更する際の注意点として残す。

### ログの再送（2026-09-17 調査で判明）

S3 のログ行数が `emails` テーブルの件数と合わないことを追ったところ、**Fluent Bit によるログ再送が実在することが分かった。**

`day=15` のパーティションに格納されていた 18,374行のうち、**4,666行は実際には 9/10 に出力されたログ**だった。同じ行は `day=10` のパーティションにも存在する。つまり**同一のログ行がS3に2つ存在する**。

```
"date": "2026-09-15T04:58:16"                          ← Fluent Bit の取り込み時刻
"log":  "[2026-09-10 05:08:12] ... sending email: 18814283"  ← 実際の出力時刻
```

**判定に使う時刻の選び方に問題がある。**

```python
"logTimestamp": (parsed or {}).get("date") or match["log_timestamp"],
```

`date` は Fluent Bit の取り込み時刻であり、**再送されると値が変わる**。同じログ行かどうかの判別に使えない。

#### 影響

Lambda は `createdAt` を実行時刻で付けるため、再送されたログ行は「今起きたこと」として保存される。

| 再送までの間隔 | 結果 |
| --- | --- |
| 1時間超（今回は5日） | 判定窓の外。誤検知しない |
| 1時間以内 | **送っていないメールを重複として通知する** |

検知の稼働開始（2026-09-16 06:22 UTC）以降、再送は観測されていない。リスクは実在するが顕在化していない。

#### 却下した案：`logTimestamp` の種類数を数える

当初は「Laravel の出力時刻を優先し、その種類数を数える」案だった。**これは採用しない**（レビュー指摘 R1）。

Laravel 行頭の時刻は**秒単位**である。同じ宛先・同じ本文のメールが EmailID 100 と 101 として**ともに `09:00:00` に送られた場合、時刻の種類数は1**になり、検知したい2通を取りこぼす。

```
再送されたログ行     → 出力時刻が同じ → 1件と数えたい      ✓
同じ秒の本物の2送信  → 出力時刻が同じ → 1件と数えてしまう  ✗
```

**この2つを出力時刻では区別できない。** 再送を潰す仕組みが、本物の重複まで潰す。

#### 採用する案：送信ごとに一意な `send_event_id` を発行する

**アプリ側で送信1回につき1つ発行し、ログに載せる。** Lambda は件数を数える際、レコード数ではなく **`send_event_id` の種類数**を数える。

```php
"send_event_id" => bin2hex(random_bytes(16)),
```

| 状況 | `send_event_id` | 結果 |
| --- | --- | --- |
| 同じログ行が再送された | **同じ**（ログの中身がコピーされるだけ） | 1件。誤検知しない |
| 同じ S3 イベントが再配送された | **同じ** | 1件。誤検知しない |
| 同じ秒に別のメールを2通送った | **異なる** | **2件。正しく検知する** |
| 同じ EmailID を2回送った | **異なる** | **2件。正しく検知する** |

**再送・再配送はログの複製であり、送信そのものではない。** 送信の瞬間に発行した識別子であれば、何回コピーされても増えない。時刻と違って衝突しない。

#### S3 イベントの重複配送にも効く

S3 自体が同一イベントを複数回配送することがある。現行のソートキーは `createdAt`（処理時刻）を含むため、**同じオブジェクトを再処理すると別レコードとして保存される**。レビューでは、同じイベントを2回渡すと2回目に重複1件・通知1回になることが再現されている。

`send_event_id` で数えれば、この経路も同時に塞がる。**Fluent Bit の再送と S3 の再配送を別々に対策する必要がない。**

#### Lambda 側の実装

`Select="COUNT"` では種類数を数えられないため、属性を取得して集合にする。

```python
kwargs = {
    "KeyConditionExpression": Key(pk).eq(pk_value) & Key(sk).gte(cutoff),
    "ConsistentRead": True,
    "ProjectionExpression": "sendEventId, recordKey",
}
event_ids = set()
# … 全ページ読み切りながら
for it in response["Items"]:
    event_ids.add(it.get("sendEventId") or it["recordKey"])
return len(event_ids)
```

**`sendEventId` が無い場合は `recordKey` にフォールバックする。** これにより次の2つが成立する。

- アプリの変更より**先に Lambda を出せる**。旧ログは現行と同じ挙動（レコード数と等価）になる
- アプリのデプロイ前後でログが混在しても、検知が壊れない

> **`ProjectionExpression` を付けても RCU は減らない。** 読み取り容量はアイテム全体のサイズで決まる。減るのは転送量だけである。`Select="COUNT"` と同じ性質。

#### 残る限界

`send_event_id` はアプリが発行するため、**アプリを通らない経路（グループA）には効かない**。またアプリの変更が入るまでは、1時間以内の再送が誤検知になるリスクが残る。

### 正常な動作でも鳴るケース（レビュー指摘 R3・許容する）

**「同じ人に同じ本文が1時間以内に2通」は、不具合がなくても成立する経路がある。** コードから確認できた2件を記録する。**本番での発生頻度は未測定。**

#### 1. 管理者向け New Room Messages

`NewGroupChatAdminMessagesEmailer.php:254` がメールへ渡すのは**メッセージ本文と送信者名**で、発言時刻もメッセージIDも含まない（`new_room_messages.blade.php:201`）。ルームと未読件数が同じなら、本文は完全に一致する。

```
09:05  通知が届く
       管理者が既読にする
09:07  同じ人が同じルームへ、同じ文面を新しく投稿
09:10  未読1件として通知が届く   ← 本文が一致。重複と判定される
```

**別の投稿に対する正しい通知である。** 「5分刻みの壁」も「10分未読」も必要としない。

#### 2. イベント参加 → 取消 → 再参加

`EventController.php:53` は参加レコードを削除・復元し、**各操作で通知を生成する**。参加メールは参加者・イベント・参加者一覧から作られ、操作時刻を含まない（`PostInteractedMail.php:125`）。

他の参加者に変化がなければ、**最初の参加時と再参加時のメールは正規化後に一致する。**

#### なぜ対応しないか

**検知そのものは正しい。** 「同じ本文が2通出た」は事実である。誤っているのは、それを直ちに不具合と解釈することのほうである。

閾値を先回りして上げると、**本物の重複まで鳴らなくなる。** 6.5年気づかれなかった事象を見つけるのが目的なので、感度を下げる判断は実測の前にはしない。

#### 運用での扱い

| | |
| --- | --- |
| まず | ドライランで発生頻度を測る |
| 頻度が低い | そのまま許容する。通知を受けたら `emails` の中身を確認する |
| 頻度が高い | 抑止リストに件名を追加する（記録は残る） |

**DMの5件の実測を16経路すべてに一般化しない。** 「本文が毎回変わるから鳴らない」が成立するのは、本文に発言時刻やメッセージ内容が入る経路だけである。

### 連投による誤検知（発生条件を整理済み・対応不要と判断）

同一スレッドへ**まったく同じ文面を連続投稿**した場合に誤検知しうるかを検討した。**4つの条件が同時に成立したときのみ発生する**ため、特別な対応は行わない。

通常は次の2つで守られている。

- 同じ tick で対象になった未読メッセージは `$messages->first()` により**1通にまとめられる**
- 本文に**分単位の発言時刻**が入るため、別の分に投稿されていれば本文が変わる

#### 成立に必要な4条件

| # | 条件 | 補足 |
| --- | --- | --- |
| 1 | まったく同じ文面を**同じ分の中**で連投 | 分が変われば本文の時刻が変わる |
| 2 | 投稿の分が **5の倍数**（:00 / :05 / :10 …） | コマンドは `*/5 * * * *` で分の頭に固定。10分後が実行の分に落ちる必要がある |
| 3 | コマンド実行の**秒位置が2件の判定時刻の間**に入る | 起動が速いほど窓は狭い |
| 4 | **どちらのメッセージも10分以内に既読にならない** | 抽出条件が `is_read = 0` のため。読まれればメールは1通も作られない |

**条件2を見落とすと過大評価になる。** tick が時間軸上に一様分布すると仮定すると確率が5倍ほど大きく出る。実際は5分刻みの固定位置で動くため、投稿の分が5の倍数でなければ、両方が次の実行でまとめて拾われる。

**条件4は誤検知が起きやすい状況と逆相関する。** 連投が起きるのは相手が見ている会話であることが多く、その場合は既読がついてメール自体が発生しない。

20秒差の連投で、条件1〜3を掛け合わせるとおよそ1〜2%。条件4を加えるとさらに下がる。

別スレッドへの投稿はスレッドURLや相手の名前が本文に入るため、そもそも影響しない。

#### 実行の秒位置（条件3）の測り方

条件3はコマンドの起動タイミングで決まる。ログから実測できる。

```bash
find <ログを展開したディレクトリ> -name '*.gz' -print0 | xargs -0 zcat 2>/dev/null \
  | grep "new-message-checker] command has started" \
  | sed -E 's/.*\[[0-9]{4}-[0-9]{2}-[0-9]{2} [0-9]{2}:[0-9]{2}:([0-9]{2})\].*/\1/' \
  | sort -n | uniq -c
```

0〜5秒に集中していれば条件3は狭く、誤検知はさらに稀になる。

#### 万一発生したときの切り分け

> **`rawLog` からメール本文は見えない。** ログの `content` は `$log_message`（`Email <id> was successfully sent!` などの処理メッセージ）であり、メール本文ではない（レビュー指摘 R6）。

通知が来た際は、`rawLog` の `emailId` を使って `emails` テーブルの `content` を引く。連投によるものかどうかはそこで判断する。

#### 検知のドライラン

**アプリ側の変更前に、過去データで検知の空撃ちができる。** `email_id` の値は行の `id` と一致するため、SQL で正規化を再現できる（MySQL 5.7 で動作）。

```sql
SET SESSION max_execution_time = 60000;

SELECT MD5(CONCAT(mail_to, '|', REPLACE(content, CONCAT('email_id=', id), 'email_id='))) AS pair_hash,
       COUNT(*) AS n,
       MIN(id) AS min_id, MAX(id) AS max_id,
       MIN(subject) AS subject,
       MIN(send_schedule) AS first_sent, MAX(send_schedule) AS last_sent,
       TIMESTAMPDIFF(MINUTE, MIN(send_schedule), MAX(send_schedule)) AS span_min
FROM emails
WHERE id >= (SELECT MAX(id) FROM emails) - 4000
  AND send_status = 'sent'
GROUP BY pair_hash
HAVING n >= 2
   AND TIMESTAMPDIFF(MINUTE, MIN(send_schedule), MAX(send_schedule)) <= 60
ORDER BY n DESC;
```

ここに出るものが、そのまま Slack へ飛ぶ通知になる。4,000行で約10時間ぶん。`content` を読むため 20,000行では30秒を超える。

#### 判断の目安

| 実測 | 対応 |
| --- | --- |
| 1日1件未満 | 許容する。通知が来たら `rawLog` で個別に切り分ける |
| 1日数件 | メッセージ通知系のみ閾値を上げる（3件以上など） |
| それ以上 | 判定窓の短縮、または経路ごとの分離を検討 |

**予測で作り込まず、実測してから判断する。** 先回りして複雑にすると、本物を取りこぼす方向のリスクが生まれる。

### 生成間隔による絞り込み（将来の候補・現時点では入れない）

「多重送信なら生成の間隔は近いはず」という仮説に基づき、判定に間隔の条件を足す案がある。

```
現在:    1時間に2件以上
追加案:  1時間に2件以上  かつ  created_at の差が N 分以内
```

連投による誤検知（別の tick で生成されるため5分前後離れる）を弾ける。

#### 今は入れない

**閾値を決める材料が無い。** 「間隔が近い」という仮説には実測上の反例がある。`inform-admin:registrants-status` は実行が遅く、**同一実行で生成された重複でも 01:37 と 03:08 のように離れる**（2026-09-17 実測）。近さを条件にすると、こうした本物を取りこぼす。

**取りこぼしは誤報より厄介である。** 誤報は通知が来るので気づけるが、鳴らないことには気づけない。狙っている誤検知（連投）は4条件が揃ったときのみで発生頻度も未測定であり、**まだ起きていない誤報のために本物を落とす条件を先に入れる**形になる。

#### 後から足せる

判定に必要な `created_at` は**今回のログ追加に含まれる**。レコードに保存されるため、間隔の比較は **Lambda 側だけで実装できる**。

| 段階 | 変更箇所 |
| --- | --- |
| 今回 | アプリ側。`created_at` を出す（デプロイ1回） |
| 後から | Lambda 側。間隔の条件を足す（いつでも変更可能） |

実際に連投による誤報が起きたら、そのときの間隔を見て閾値を決める。

#### 参考：時刻の2軸

| ログ項目 | 中身 |
| --- | --- |
| `created_at` | メールが生成された時刻 |
| `scheduled_at` | メールが送信された時刻（`send_schedule` が送信直前に上書きされるため） |

`updated_at` は送信時の `save()` で更新されるため `scheduled_at` とほぼ同値であり、追加しても情報が増えない。

### 検知の実効性

本仕様で捕捉できるのは「送信時点で同一宛先・同一本文が1時間内に2回以上出現する」場合に限る。今回見つかった事例は3秒差であり問題なく捕捉できるが、**24時間以上あけて同じものが届くケースは対象外**である。
