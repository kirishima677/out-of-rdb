# レビュー依頼：OAメール多重送信検知の現状

2026-09-23 時点。第三者レビュー用に状況を自己完結でまとめたもの。

---

## 1. 何を作っているか

Official-Alumni（以下 OA）で、**同じメールが多重に送信される事象を検知して Slack に通知する仕組み**。
AWS 上の独立した Lambda で、アプリ側のログを読むだけ。アプリの動作には介入しない。

担当は1名（SRE/インフラ）。アプリ本体（Laravel）は別チームの管轄で、こちらは読み取りのみ。

### 検知したい事象は2種類ある

| # | 事象 | 判定キー | 状態 |
| --- | --- | --- | --- |
| 1 | **同じメールが2回送信された** | EmailID（`emails` テーブルの行ID） | **本番稼働中**（2026-09-16〜） |
| 2 | **同じ人に同じ内容が複数通届く** | 宛先 + 本文 | **仕様確定・未実装** |

本レビューの主対象は **2** の仕様である。

---

## 2. 現在の構成（1が稼働中）

```
Laravel worker（EvenSendEmails / OddSendEmails）
   │  "success sending email: <id>" をログ出力
   ▼
Fluent Bit（約10分間隔でフラッシュ）
   ▼
S3  hkz-log-archive
   │  service=worker/env=production/log_source=laravel-app/...
   ▼  ObjectCreated イベント（フィルタなし）
Lambda  detect-mail-duplicates-prd
   │  ① プレフィックス判定 → ② 正規表現で抽出 → ③ DynamoDB に保存 → ④ 件数を数える
   ▼
DynamoDB  prd_mail_send_log_events   （PK=EmailID, SK={createdAt}#{sourceKey}#{行番号}）
   │  1時間以内に同じ EmailID が2件以上
   ▼
SNS → メール / Slack Webhook
```

## 3. 構成上の制約（レビュー時に前提として必要）

### S3 通知フィルタが効かない

S3 は同一バケット・同一イベント種別で**条件が重なる通知設定を許可しない**。

> Configurations on the same bucket cannot share a common event type.

本番と STG を分けるにはプレフィックスフィルタが必要だが、**フィルタを付けると本番・STG のどちらにもイベントが届かなくなった**（適用から15分以上待っても変わらず）。イベント中のキーが URL エンコードされている（`service%3Dworker/...`）ことが原因の仮説だが**未検証**。

結果として**フィルタなしで本番のみ登録**し、絞り込みは Lambda 側の `TARGET_KEY_PREFIX` が担っている。

**代償**

- 無関係なオブジェクトでも Lambda が起動する（約92%が空振り）。費用は月20〜30円で問題なし
- CloudWatch Logs のノイズが大きい
- **STG は通知エントリを本番に譲ったため停止中**

**安全性は二重に担保している。** コードが `GetObject` の前にプレフィックスで捨てる。加えて IAM の `s3:GetObject` が本番プレフィックス配下に限定されており、コードが壊れても `AccessDenied` で止まる。

### Fluent Bit のログ再送が実在する

2026-09-17 の調査で確認。**9/10 のログ4,666行が9/15に再送された。**
現在 `logTimestamp` には Fluent Bit の取り込み時刻を優先して入れているため、再送されると別の行として扱われる。

今回の再送は5日遅れで判定窓（1時間）の外だったが、**1時間以内に再送が起きると誤検知する**。対処案は「Laravel の出力時刻を優先し、件数を `logTimestamp` の種類数で数える」。未実装。

### S3 のパーティションパスは Fluent Bit の取り込み時刻

ログの出力時刻ではない。集計時に2度この罠を踏んだ。

## 4. 実装予定の機能（本レビューの主対象）

### 検知の定義

| 項目 | 値 |
| --- | --- |
| 判定キー | **宛先ハッシュ + 本文ハッシュ** |
| 判定窓 | 1時間 |
| 閾値 | 同じキーが2件以上 |

### アプリ側の変更（別チームに依頼する内容）

`EvenSendEmails.php:378` と `OddSendEmails.php:378` の `createLog()` に項目を追加する。

```php
$key  = (string) config('mail_dup.hash_key');
$to   = is_array($email->mail_to) ? implode(',', $email->mail_to) : (string) $email->mail_to;
$body = preg_replace('/email_id=\d+/', 'email_id=', (string) $email->content) ?? (string) $email->content;

$logData = [
    // 既存項目 ...
    "created_at"   => $email->created_at,
    "company"      => trim(substr(strrchr('|' . $email->mail_from, '|'), 1)),
    "language"     => $email->language,
    "content_hash" => substr(hash_hmac('sha256', $body, $key), 0, 16),
    "mail_to_hash" => substr(hash_hmac('sha256', strtolower(trim($to)), $key), 0, 16),
    "subject_hash" => substr(hash_hmac('sha256', (string) $email->subject, $key), 0, 16),
];
```

加えて `config/mail_dup.php` を新規作成し、環境変数 `MAIL_DUP_HASH_KEY` を全ワーカーに設定する。

### AWS 側の変更

- 新規 DynamoDB テーブル `prd_mail_send_log_events_by_content`
  - PK `mail_to_content_hash` = `"<mail_to_hash>:<content_hash>"`
  - SK `recordKey` = `{createdAt}#{sourceKey}#{行番号}`
- Lambda のコード変更（本文重複の判定を追加、`logTimestamp` の優先順位修正）
- IAM に新テーブルへの権限追加
- 環境変数 `SUPPRESS_SUBJECT_HASHES`（既知事象の通知抑止）

## 5. 設計判断とその根拠

### 件名ではなく本文で判定する

実測が決め手になった。ある受信者は「メッセージが届きました」を**50時間で104通**、最短4分間隔で受け取っていた。本文ハッシュを比較したところ**5件すべて異なった**（本文長 15,769〜18,421）。本文にメッセージ内容と発言時刻が含まれるためである。

| 判定方法 | この経路での結果 |
| --- | --- |
| 件名で判定 | 毎時鳴り続ける。使えない |
| 本文で判定 | 鳴らない。正しい |

### 本文ハッシュの前に `email_id` を正規化する

開封トラッキング画像（`layout/container.blade.php:11`）に `email_id` が埋め込まれており、**同じ内容でも毎回本文が変わる**。テンプレート全数調査の結果、本文に入る一意な値は**この1箇所のみ**だった（時刻・乱数・UUID・トークンは0件）。

### 3つのハッシュを別々に出す

組み合わせは Lambda 側で作れる。分けておけば、後から別の検知軸（同じ本文の大量配信など）を足すときに**アプリ側の再デプロイが不要**になる。

### HMAC にする（素の SHA-256 にしない）

ログに残るハッシュからメールアドレスを逆引きされないため。候補が限られる値は総当たりで復元できる。
**鍵はアプリのワーカーのみに必要で、Lambda には不要**（比較するだけで計算しない）。

### 別テーブルにする（既存テーブルに相乗りしない）

名前で用途が分かること、段階的に廃止する可能性があること。

### 判定窓を1時間にする

- これより長くできない理由：日次の登録リマインドが同じ宛先に同じ本文を送るため、24時間以上にすると全件誤検知になる
- 短くしてもよいが、EmailID 検知と揃えている

## 6. 既知の不具合（検知の初日から鳴る）

`InformAdminAboutNewRegistrationsStatus`（`inform-admin:registrants-status`、日次 9AM JPT）のループ構造に不具合があり、**同じ管理者へ同じ本文が複数通送られている**。

```php
foreach ($registrants as $registrant) {              // :113
    $company = Company::where('id', $company_id)->first();      // :115
    $company_users = User::whereHas('companies', ...)->get();   // :117
    foreach ($company_users as $user) {              // :125
        AlumniIncompleteRegistrationEmail::create(... $registrant ...);  // :129
    }
}
```

登録者ごとに全管理者へ1通ずつ作られるため、登録者が3人いれば管理者は3通受け取る。
2026-09-17 の本番データで **1日3通** 受け取っている受信者を確認済み。約6.5年前から存在する。

**アプリチームとは「ログは出すが Slack へは通知しない」で合意済み。** 修正時期は未定。

そのため `subject_hash` による**抑止リスト**を実装する。除外（記録しない）ではなく抑止（記録するが通知しない）にしているのは、修正されたことを記録側で確認したいため。

## 7. 対象メールの分類（一覧表44行を分類済み）

アプリチーム提供の `Email and Notifications - Emails_new`（44行）を、`Sending Schedule` と `Email Creation Schedule` の2列で分類した。

| グループ | 見分け方 | 件数 | 扱い |
| --- | --- | --- | --- |
| A | Sending = `Immediately` | 4 | **検知対象外**（worker を通らずログが出ない） |
| B | Creation = `Every 5 mins` | 16 | 鳴らない（本文が毎回変わる） |
| C | Creation = `Daily` / `Weekly Scheduled` | 3 | 窓の外。**うち1件が上記の既知不具合** |
| D | Creation = `On Trigger` | 18 | **本来の検知対象** |
| — | 記載なし | 3 | 未確認 |

**グループA（パスワードリセット等）はコード側でも裏が取れている。** `OAResetPassword` は `emails` に行を作るが `send_status = 'cancelled'` で worker は送らない。`ForgotPasswordController:160` は `Mail::send` で直接送信する。
裏を返すと、**この4経路で暴走が起きても検知できない。**

### 死活監視の既知の限界

`Invocations` 監視は**起動の92%が対象外オブジェクト**であるため、「バケット全体が生きているか」しか見ていない。**メールログだけが届かなくなった状態は検出できない。**
それを見るには `Matched successful mail send` のメトリクスフィルタが必要だが、夜間は送信ゼロの時間帯があるため窓を長く取る設計が要る。

## 10. レビューで特に見てほしい点

1. **判定キー（宛先+本文、1時間、2件以上）で誤検知は十分に防げているか。** 見落としている「正常なのに同じ本文が短時間で複数通出る」経路はないか
2. **`email_id` の正規化だけで足りるか。** 本文に入る一意な値の全数調査に漏れはないか
3. **ログ再送（Fluent Bit）への対処案は妥当か。** 「`logTimestamp` の種類数で数える」で十分か
4. **DynamoDB のキー設計。** PK `"<mail_to_hash>:<content_hash>"` / SK `{createdAt}#{sourceKey}#{行番号}` にホットパーティションや取りこぼしのリスクはないか
5. **抑止を `subject_hash` で行うことの是非。** `generic_notification` を12件が共有しており、件名だけが識別子になっている
6. **アプリ側の変更（`createLog()` への追記）が本番の送信処理を壊すリスク**
